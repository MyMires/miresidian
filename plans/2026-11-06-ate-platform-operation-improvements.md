# LS-D550 复盘：测试平台工具与 skill 优化方案

日期：2026-11-06。状态：待审阅；本轮仅调研与方案归档，未实施工具、skill 或业务项目修改。

## 1. 目标、范围与依据

用户要求根据 LS-D550 操作中的八类问题给出优化计划。目标是减少为一次业务修改临时编写的定位、接口核对、检查汇总及备份脚本，让修改过程能够从接口证据追溯到写入与恢复结果。

本方案保留 `ate-project` 与 `vi-engine` 的独立命令、进程和版本；通过版本化 JSON 交换数据，便携 skill 负责组织流程。优先扩展现有实现，不新建通用插件平台，不把功能并入 Miresidian 运行时，也不默认增加第三个常驻服务。

本轮授权为“给出计划”，不包含后续实施、硬件操作、驱动替换、发布或部署。LS-D550 原始项目、实际 DUT/CAN/恒惠驱动及本次检查日志尚未取得；“原有 6 条缺失变量错误”等为用户复盘提供的验收输入，不能记为本轮重现结果。

## 2. 总体流程和职责

一次业务修改按以下顺序组织：

1. 读取三表、revision 与当前检查，冻结业务修改基线；发现重名目标时列出候选，不猜定位。
2. 解析相关设备的入口 VI、包装层及实际依赖 DLL；获取有来源证据的接口快照，并与缓存比较。
3. 如需刷新缓存，先预览差异并建立本次操作备份，使用已验证快照更新，重读后检查等价性。
4. 按章节/步骤定位构造操作，在内存中完成章节、通道、输出和变量联动，输出内容变更预览及问题摘要。
5. 提交写入前再次核实三表 revision、相关驱动/缓存哈希和预览操作摘要；任何前置输入变化都重新读取与预览。
6. 写入后重读、重新检查并更新清单；异常时按照清单恢复，核实最终文件与哈希。
7. 文件验证与平台运行验证分别报告；涉及供电恢复时额外执行已约定的正常/异常退出验收。

职责：`vi-engine` 负责接口提取与缓存；`ate-project` 负责三表编辑、验证、预览和项目侧清单/恢复；skill 组织两工具与业务证据。跨工具使用同一 operation_id 和清单结构，各工具只写自己负责的文件。联合操作不是跨目录、断电级原子事务。

## 3. 具体设计

### A. 统一接口证据与缓存管理（高优先级）

统一快照至少包括：schema_version、驱动标识、适配器类型、入口和依赖文件路径、文件 SHA-256、可取得的文件/程序集版本、查询时间、提取工具版本、原始返回、解析后的初始化/函数契约、完整性与验证状态。无法取得版本时明确 unknown，不用文件时间或哈希冒充版本。

- .NET：优先静态读取程序集元数据及已有契约，不执行初始化器或业务方法；元数据不能证明平台的名称/参数映射时，补充已验证的包装层适配规则。
- 原生 DLL：静态列出 PE/导出证据；仅有导出名不能推导参数类型、顺序、编码、默认值或生命周期。只有已有契约文档、随包元数据或已验证的查询协议，才生成完整平台接口。缺少依据时返回 partial/unsupported，阻断依赖该接口的修改及缓存刷新。
- VI：复用现有查询，仅允许明确的元数据入口；记录 LabVIEW、方法与位数及包装链。多入口不再任取第一个，必须唯一定位或显式指定。
- 动态查询与静态检查分开。查询子进程设超时、取消和资源释放；权限拒绝、COM 不可用、超时、崩溃均返回具体阶段及已完成结果。隔离不能撤销设备副作用，不能仅凭命令叫查询就声称无副作用；未知方法不自动调用。
- 同时保留缓存快照与实时/静态快照，按初始化项、函数、参数顺序/类型/默认值/选项、输出及包装映射比较；区分新增、删除、变更和仅表示方式差异。

缓存更新流程固定为“预览差异 → 校验前置哈希 → 备份 → 从已验证快照写入临时文件 → 替换 → 重读解析对比 → 记录结果”。快照、适配器/映射及依赖任一改变都使旧验证证据失效。未知来源、部分查询、签名不可表达、序列化丢失信息或并发改写时停止；回读不一致时恢复备份并报告恢复结果。

保持旧 `driver-info --source` 的含义，新增显式验证/缓存管理入口；不静默改变 auto 的执行行为。旧 `--write-paras` 接入相同的备份与回读机制。新接口数据必须带证据；旧 JSON 继续可读，但来源/哈希缺失时标记 unverified，不自动升级为可信。

### B. 检查结果和变更预览（高优先级）

新增 summary 和可选文本报告，保留现有 JSON 明细与退出码。报告首屏包括：本次新增错误、原有错误、待确认事项、未检查范围、已消除问题，以及与本次修改相关的阻断项。未检查范围与已发现的输入歧义分开，不能统一隐藏进警告。

- apply 继续使用同一基线的内存前后检查；独立 check 没有基线时不判断新旧，只报告当前问题。跨多次 apply 的整次业务比较，需要显式保存三表基线、revision、接口快照哈希和检查器版本；不兼容或输入条件不同则标记不可比较。
- 分类前比较原始问题身份，分类后再聚合展示。同一规则、对象、参数、值和原因在六通道一致时显示一项 `通道 1–6`，保留 6 个可展开位置及原始计数；值、来源或新旧分类不同的项不能合并。
- 保留原有错误且与本次修改无关时不自动修复；修改影响到旧问题时明确标出。新增明确错误继续阻断；本次目标依赖的接口未知、目标不唯一或变量绑定歧义也须有可核对的阻断原因。检查不全不得显示“全部通过”。
- 预览按原始行身份比较内容，区分新增、删除、字段修改、显式移动与被动行号位移。默认报告只展开内容变化；被动位移按区间汇总，显式章节移动显示来源/目标和步骤数。编码、换行、空列等真实文件变化单列，不能因正文相同而隐藏。
- 保留旧 preview 字段作为兼容明细，新增聚合视图/显示模式；默认面向用户的报告采用内容视图，既有脚本不因 JSON 字段突然消失而失效。

### C. 章节、通道、变量与输出（中优先级）

- 主表新增章节选择器（章节名及必要上下文）和相邻章节 before/after 定位；重复章节或步骤匹配必须拒绝并列出候选。选择器在 revision 锁定的快照上解析，批次中用稳定的内部行身份跟踪，新章节可使用批次局部别名，避免人工模拟行号。保留旧物理行号接口。
- 新增章节整体插入、移动、启用/禁用；完整携带备注、条件、线程、重试、子步骤顺序和各自状态。首尾常驻章节继续保护。
- 禁用优先仅设置章节门控并保留子步骤字段，但必须先验证平台的门控语义。平台不支持时，使用操作清单保存逐步骤状态并明确恢复条件；未经验证不开放会错误恢复子步骤的切换操作。
- 增加通道集合/共同参数与逐通道覆盖，先展开为现有六通道结构，再验证签名；没有指定的通道保留原值，禁止从空值猜测是否启用。
- 变量报告按静态流程首次产出/引用位置给出建议顺序，保留用户已有顺序，重排需显式操作。条件、线程和重试使运行顺序不确定时标记可能位置，不能承诺真实执行顺序。
- 对明确输出引用检查缺失变量、类型/判定范围与已知输出契约的一致性；同时检查重复名、未使用变量、使用前可能未赋值。解析不确定的表达式保留待确认。量纲/范围缺少契约时不自动推断；DUT/治具区分作为命名建议，不直接批量改名。
- 提供步骤输出与变量定义的联动预览，按同一批内存操作提交，任一失败均不写入；引用更新复用现有 rename 的明确绑定规则。

### D. 结束恢复与联合备份（贯穿所有阶段）

skill 必须在方案中分别写清正常结束、步骤失败、手动停止、平台异常退出的设备目标状态、触发机制及验证证据；断电等机制覆盖不到的情况明确列为未覆盖。普通末尾“恢复 24 V”只能证明计划在正常路径执行。

先对平台源码/文档及目标版本做能力核查，确认是否有结束复位钩子、错误处理、停止回调或独立清理机制。只有对应路径实测执行、读回状态和失败提示成立，才标记该路径已验证。宿主超时后终止查询子进程不等于撤销 LabVIEW 调用或恢复设备。没有可靠机制时报告缺口与人工恢复步骤，不通过改名或添加末尾步骤宣称保障。

联合清单以显式文件集合记录三表、缓存、入口 VI、依赖 DLL 和替换目标：原路径、是否原先存在、原/目标哈希、备份路径、所有者工具、预览操作哈希、接口证据、每文件状态和错误。驱动文件可仅备份；替换只在业务操作明确包含替换时执行，不在编辑项目时顺带替换 DLL。

全部必要备份及哈希校验成功后才能开始本次写入。逐文件记录 staged/written/verified/restored/restore_failed 等状态；写入前重新核对预期哈希，避免覆盖外部变更。恢复默认先预览，校验备份与当前文件哈希，不覆盖无法确认的后续编辑；恢复前原本不存在的文件按清单处理并复核。DLL 占用、权限失败、不同卷替换和中途崩溃均不能伪装为完整成功；重启后可读取清单判断待恢复集合。

## 5. 分阶段实施及验收

阶段编号表示交付顺序，不构成当前实施授权。可靠性约束从第一阶段生效，不把现有缓存写入的恢复问题全部推迟到最后。

| 阶段 | 工作与依赖 | 可核对的通过标准 |
| --- | --- | --- |
| P0：固定样本/契约 | 获取脱敏 LS-D550 三表、原始检查与三类驱动及包装链；核实平台版本/退出机制；制定快照、摘要、清单 schema 与命令参数；先将具体 CLI 示例补入方案 | 一份基线可重复读取；6 条旧缺失变量错误可定位；明确 .NET/原生/VI 的可提取范围与阻断条件；没有样本的项保持未验证 |
| P1：可读性与基线 | 扩展检查聚合、内容预览、跨批基线；同步三表 skill 报告流程 | 不增加错误的修改显示新增 0、旧错误 6；同一六通道问题显示一组且明细完整；新增同名错误不被旧错误掩盖；插入少量 CAN 步骤时，不逐条展开后续数百行位移；无基线不猜新旧 |
| P2：接口与缓存 | 复用 VI 查询，加统一证据与两类 DLL 适配；缓存差异、备份、哈希与回读，接入操作清单；P0 的签名来源必须已明确 | 三类样本可证明接口来源，或明确返回 partial/unsupported；模拟过期缓存能展示差异；权限拒绝/超时/多入口不误用缓存；来源不明零写入；并发变更阻断；回读失败恢复原缓存并核验哈希 |
| P3：业务编辑 | 按名称/邻章定位、批次内部身份、章节整体编辑、通道集合、输出与变量联动 | 无需调用方计算插入后行号；重名拒绝；章节移动内容/顺序保真；禁用再恢复不改变原先禁用的子步骤；六通道覆盖正确；变量与输出不存在半完成写入；原始编码/空行/未改字节保留 |
| P4：联合恢复与平台验收 | 完成跨工具清单恢复/续查；验证结束机制；完整 skill 与整合包 | 在第二/第三文件失败、DLL 占用、备份失败、写后校验失败、进程中断和恢复冲突场景下，列清已写/已恢复/待恢复；恢复副本哈希一致；LS-D550 副本可在原编辑器打开；正常结束/失败/停止等分别记录设备状态证据 |

静态解析和编辑行为使用最小代表夹具及故障注入测试；Windows .NET/原生驱动、LabVIEW 和目标平台能力需实际环境验收。硬件恢复先用模拟器或受控条件，再按业务允许范围实测，不能自动用未知命令尝试恢复。只运行改动直接影响的测试、格式/静态检查和目标构建，证据齐备即停止，不扩展为 Miresidian 全量测试。

每阶段交付：更新后的方案/决策、实际命令与返回示例、组件文档/迁移说明、针对性验证结果及剩余未检查范围；最终以 LS-D550 一次完整业务修改的操作清单回放验收。平台未验证不阻止报告已完成的文件功能，但不得宣称业务运行或异常恢复已经通过。

## 6. 版本、提交与发布评估

- 本轮版本影响：无；仅归档方案，不改变规范要求、可构建/可调用/可交付行为，不升级框架或工具、不修改锁文件、不生成产品版本标签。若归档提交，提交说明记录上述理由，核对既有标签不移动。
