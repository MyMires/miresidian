# 框架与 Node 项目先方案后实施规范

日期：2026-11-06。初始状态：方案先行落盘，随后按下列步骤实施；当前状态：文档与 skill 实施、验收完成，提交及标签核对记录见对应 Git 提交与交付回复。

## 需求与授权依据

用户明确要求：创建或更新 Node 项目必须先计划并形成方案文件，禁止直接实施；框架自身更新同样先更新方案文件再实现功能；实际实现方式必须严格遵循计划文件。本次仅落实这些维护规则，不改变产品行为。用户已明确授权本次规范与 skill 更新；不追加产品设计、运行时改动、发布或部署。

## 范围与设计

- 框架强制入口为根 AGENTS.md，完整规范写入 docs/coding-standards.md，覆盖框架、组件、宏、工具和 Node 的新建、修复、维护、重构与升级。
- 默认在项目 plans/YYYY-MM-DD-主题.md 建立任务方案；已有同任务方案先更新。方案需有目标/非目标、现状与版本依据、设计与端到端调用路径、接口/资源/错误契约、影响文件、版本影响、分步实施及验收证据。纯规范或小改动允许缩短内容，不豁免文件先行。
- 方案落盘前仅做只读调研与方案编写；项目模板初始化、源码/测试实现、依赖安装升级、构建交付和发布均属于后续实施。新项目尚无目录时先在工作区规划目录落盘，实施阶段按计划归档，禁止用初始化绕过前置条件。
- 方案是实现依据，实施步骤必须对应文件内的设计和验收项。偏离前先修订方案、解释原因与影响；涉及目标、架构、接口、资源状态/生命周期、兼容性或验收标准的变化，先按用户要求完成必要确认，不能先做后补。已有明确授权与确认可复用；用户要求先审方案时必须等待，不能用一般授权或沉默代替该确认。保留既有新建/整体构建 Node 的方案确认要求。
- 更新仓库 skill 主文档、references/review.md、维护规则和 UI 元数据，新增 references/planning.md 提供可直接采用的方案结构与一致性审查要求；安装副本同步完整目录，包括维护规则和所有引用。
- 不修改 Rust 源码、宏标签、模板、依赖、锁文件、工具命令和交付技术契约。不新增自动检查程序；版本检查与引用校验不能宣称自动证明方案语义或先后顺序。

## 实施顺序与验收

| 步骤 | 变更文件 | 实施内容与验收证据 |
| --- | --- | --- |
| P1 | 本文件 | 先落盘需求、范围、设计、版本评估、实施及验收；实施后补充实际状态与结果，保留原方案及调整依据 |
| P2 | AGENTS.md、docs/coding-standards.md | 强制先方案后实施；明确方案内容、严格按文件实施、变更控制与逐项验收；审查框架更新和小修复都无跳过入口 |
| P3 | skills/miresidian-node/SKILL.md、references/planning.md、references/review.md、AGENTS.md、agents/openai.yaml | 新建及局部更新都先形成方案；去掉模板初始化可提前执行及局部维护绕过计划的旧表述；实施和交付引用同一任务方案 |
| P4 | 安装副本完整目录 | 修改前比较、备份两份完整副本，修改后完整同步；比较文件清单与 SHA-256，检查格式、链接/锚点及 UI 元数据 |
| P5 | CHANGELOG.md、CHANGELOG.en.md | 归档带日期的规范修订及版本影响；运行版本门禁、差异检查，提交后核对原版本标签未移动 |

审查场景：新建 Node、小范围修复旧 Node、更新框架租约/接口、仅规范更新、实施时发现关键设计需调整。每个场景均检查方案先行、执行授权边界和实施证据对应，不运行无关全量构建或硬件验证。

## 版本与交付判断

版本影响：无；本任务只更新维护规范、任务方案和 Node skill，不改变可构建、可调用或可交付行为。框架保持 0.25.0，lease 保持 0.17.0，其他组件、ABI、协议、锁文件及既有版本标签不变。使用纯规范提交并说明理由，不发布 registry。

- P1：先建立本文件，再备份完整原始 skill 双副本；原始两份文件清单和 SHA-256 一致，备份位于系统临时目录，未带入仓库。
- P2：根 AGENTS.md 加入强制入口，开发规范增加方案文件门禁、内容表、严格按方案实施、调整控制和需求到验收的对应关系。小改动与框架自身更新均无跳过入口。
- P3：Node skill 将局部维护纳入方案先行，移除模板初始化可提前进行的旧规则；新增 planning.md，并同步主流程、review.md、维护规则及 UI 提示。具体 API/版本仍查询官方资料，未增加固定适配版本或产品实现约束。
- P4：仓库与安装目录的全部 5 个文件清单、SHA-256 一致。标准库对两份当前简单 YAML/frontmatter、UI 元数据及 13 份 Markdown 的 35 处本地链接/锚点校验通过；通用 quick_validate.py 因环境缺少 PyYAML 未能运行，未将其记为通过。
- P5：版本门禁和 git diff --check 通过；修改范围限定为规范、方案与 skill，产品源码、模板、清单、锁文件和工具命令未改变。规范修订以带日期条目归档，不触发产品升版、不移动既有版本标签；提交记录作为本任务归档依据。

五类场景审查：新建 Node（含目标目录未创建）先在规划目录形成文件并确认方案，再初始化；旧 Node 小修复先写短方案，保留实际版本及范围；框架租约/接口更新先明确资源共享粒度、状态和生命周期再改代码；纯规范更新同样先文件后实施并评估版本影响；发现关键方案不可行时只停止受影响步骤，先修订并满足必要确认条件，再继续。均无事后补方案或擅自降低验收的合法入口。

本次未偏离原方案，未执行产品构建、设备测试、部署或发布。上述流程为规范与人工审查门禁，未增加自动语义/时序执法工具，不声称版本检查能证明实现完全符合方案。
