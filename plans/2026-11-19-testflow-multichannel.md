# TestFlow 0.14：按通道映射调用参数

日期：2026-11-19。所属组件：miresidian_testflow_windows；拟议目标版本：0.14.0。

## 当前决策与授权

用户要求讨论 TestFlow 多通道测试方案，参考测试平台表格，比较多种语法，并明确“优先采纳 C”。当前优先采用“业务方法名 + JSON 通道对象”，单通道与多通道使用同一结构；不增加 MultiChannel 包装指令。

用户随后询问多通道 Config 和相同参数的表达，明确选择“方案一吧，更新计划”。按此选择，通道对象采用单通道、通道集合或连续范围作为键，一份参数数组展开到所选通道；不采用 channels/input 分离的另一种对象结构。

用户进一步指出不应把每通道独立 Config 留作范围待定项。此前将选择仅收窄到参数简写的解释不再作为当前范围：每通道独立 Config 纳入本次首版设计与验收，补齐映射、初始化、派发和清理；现有 DLL 单请求仅一份 Config 是执行器需要适配的约束。范围确定不等于产品代码已获实施授权，具体设计仍随本文件收敛。

用户在审核后要求补齐 DLL 多通道及租约特性测试。当前范围同时包含真实 DLL 多通道派发、自动断言与预期错误、多宿主租约验收、并发和故障测试；测试编排优先复用已有 DLL 验证程序。此次修订优先于下方历史记录中的顺序派发草案和断言未纳入范围的判断。

本轮仅更新原方案与选择依据，不开始产品实现、升版、推送或发布。选定语法不代表下文其他建议已获确认，也不代表该语法已由当前工具支持。

```text
# 单通道形式
发送({"ch1": ["AA", "hex"]})

# 多通道形式
发送({
    "ch1": ["AA", "hex"],
    "ch3": ["BB", "hex"]
})
```

此前比较：A 为按位置排列的通道数组，跳号需要 null 占位；B 为 ch1 = [...] 命名参数；C 为标准 JSON 通道对象；D 为每个业务参数携带通道值数组。保留其他方案作为讨论记录，不同时引入多套新语法。早期 MultiChannel 包装指令已被用户否决。

## 已选择：通道集合、范围与相同参数

同一键选中的通道使用同一份参数内容，展开后按通道编号建立槽位。示例均为未来语法，尚未实现：

```text
# 单通道
发送({"ch1": ["AA", "hex"]})

# 不连续通道使用相同参数
发送({"ch1,ch3,ch5": ["AA", "hex"]})

# 连续六通道使用相同参数
发送({"ch1-ch6": ["AA", "hex"]})

# 不同组使用各自的参数
发送({
    "ch1-ch3": ["AA", "hex"],
    "ch4,ch6": ["BB", "hex"]
})
```

- 键的草案语法限定为 chN、逗号连接的 chN 集合或包含两端的 chN-chM 范围。编号为无前导零的正整数，键内不带空白；范围要求 N <= M，ch1-ch1 与 ch1 等价。暂不增加集合内嵌范围、通配符或引用表达式。
- 在同一键或不同键中重复选中任何通道均报错，包括重复 JSON 键、集合重复项、范围相交及单通道与组重叠；错误指出冲突通道与来源键，不按属性顺序覆盖参数。
- 先检查编号、范围端点与容量，再展开范围和分配槽位。集合顺序与对象属性顺序不改变通道定位；最终按数字编号排列，ch10 不排在 ch2 前面。结果范围、显式 null 与容量细节仍按下文待定项收敛。
- 相同参数表示每个选中槽位获得相同输入，范围键本身不是广播指令。同一对象的 DLL 多通道路径中，Sequential/Parallel 各执行有效通道；Broadcast 仍只以通道1为执行源，缺少通道1时整批跳过，不改用集合中最小的有效编号。不同对象的跨实例路径不复制一次结果，具体派发以测试设计章节为准。

## Config 归属：共用配置与每通道配置均纳入首版

当前框架的一次多通道请求只使用一份 Config，现有形式继续表达所有输入槽位共用该对象：

```text
Config("COM1", "115200")
InitDevice()
发送({"ch1-ch6": ["AA", "hex"]})
CloseDevice()
```

每通道配置复用已选的单通道/集合/范围键。同一条业务语句可以选择不同 Config 的对象，并给它们提供相同或不同的业务输入：

```text
Config({
    "ch1": ["COM1", "115200"],
    "ch2": ["COM2", "9600"]
})
InitDevice()
发送({"ch1-ch2": ["AA", "hex"]})
CloseDevice()

# 相同配置的简写；不承诺创建六个独立对象
Config({"ch1-ch6": ["COM1", "115200"]})
```

以下为本范围内的具体设计草案，实施前须落实所列身份与能力检查，不能以移出范围代替设计：

- Config 只选择配置，不隐式初始化。映射先整体校验键、冲突、容量及配置数组，再替换当前选择；缺少 Config 的业务通道在发出任何该行业务调用前报错，不静默借用其他通道。切换配置选择不擅自关闭先前已打开对象；已初始化对象仍由生命周期记录负责清理。
- InitDevice() 为当前配置映射中的目标完成初始化，CloseDevice() 关闭当前选择涉及的已打开对象；两者原有的普通 Input 参数按实际方法签名传入，统一参数可用于各目标。初始化 Input 按通道区分的具体语法需在实现前补齐，不能假定示例中的零参数适用于所有节点。全局 CloseAllDevices() 保持全局关闭语义。
- 运行时仍以 Config 组合键或显式 Handle 判定对象身份与冲突，工具不从 COM 名称、通道号或完整数组字符串猜测实际身份。相同身份与一致配置复用；不同 Handle 不合并。生命周期记录必须能识别已存在/本次新增对象及各通道绑定，关闭或回滚时不能重复销毁复用对象，也不能误关本次初始化前已存在的对象。
- 独立对象需要节点具备同时保留多个实例的能力；默认单实例节点会在不同 Config 初始化时替换旧对象，因此不能盲目循环初始化后宣称多个通道均可用。首版必须有可靠的能力/身份检查，在有副作用前拒绝不支持的组合；现有 DLL 元数据若不足，补齐最小可验证契约并独立评估框架/ABI 版本，不根据显示名称猜能力。
- 此前每通道配置一律依次发普通请求的草案已修订：本行业务选中的多个通道若定位同一运行时对象，与共用 Config 一样组织一次真实 DLL 多通道请求；定位不同对象时才使用跨实例派发。不得因 Config 改用通道映射写法就绕过同一对象的执行策略。具体边界和证据见测试设计章节。
- 在每行开始业务前验证配置绑定和初始化状态；跨实例派发遇到业务错误停止后续未开始的通道，保留已完成结果和失败通道/配置上下文，不声称有回滚；DLL 多通道请求的失败按框架自身策略处理，不能在宿主重写成逐通道停止。初始化部分失败清理本次新增且由流程持有的对象。无显式匹配的预期错误时停止流程；匹配预期错误时允许后续语句检查旧对象或显式恢复，不自动重试该行。正常结束、业务失败或协作停止时均尝试清理仍持有的对象，逐项保留清理失败信息，不让后续成功或清理错误掩盖原始失败；强制终止进程不承诺执行 finally。
- Rust 静态检查器记录所选配置模式和通道覆盖、初始化与关闭的基本流程；实际 Config 默认值、身份/Handle、节点能力与冲突在 DLL 加载后校验。必须新增每通道配置状态与生命周期记录，不能继续将单个 selectedConfig/原始字符串集合视为足够的实现。

## 现状与资料依据

- 当前工具源码版本为 0.13.0，flow.rs 与 runner.ps1 均按物理行解析调用，仅接受字符串参数；尚不支持对象参数或多行调用。旧形式如 发送("AA", "hex") 已存在，兼容策略须明确。
- DLL 通过 GetFunctions/GetInitConfig 提供方法与初始化元数据；现有执行器按 TB 文本契约解析，ABI 7–9 使用三参数入口，ABI 10 使用单 JSON 请求入口。platform = 0 使用 DLL 固定默认平台，不保证自定义 DLL 的默认平台一定是 TB。
- TB 适配器以 Input[0] = "共享" 识别多通道输入，以后续每个字符串表示一个槽位，槽位内部按英文逗号拆分并 trim；输出将各通道字段用逗号拼接，不能无损反推出字段边界。
- 设计参考为本地 ate_editor/src/types/index.ts、RowEditorDialog.vue、DevEditorDialog.vue、types/__tests__/index.spec.ts，以及 ate-project/README.md 和合成测试。主表区分方法、ch1–ch6 输入、输出映射、线程和共享列；驱动表另存各通道初始化参数。编辑器源码未证明线程/共享列与框架策略的运行时对应关系，不直接映射。
- 批量读取真实客户工程行曾被自动审批拒绝，原因是提取范围超过必要样本且可能含敏感数据；本方案不引用客户行内容，也不把合成样例视为真实平台或硬件验证。

## DLL 多通道与租约特性测试设计

### 真实调用路径与可观测证据

- 同一对象的请求只要需要多个通道槽位（包括保留前置跳过位置），必须通过 DLL C ABI 发送一次多通道请求，不能宿主逐个调用后拼出相同返回值。槽位是否有效由约定的校验层及 DLL 判定，不能先过滤无效输入再压缩位置。对象判断依据是 DLL 提供的实际身份/能力契约；同一对象的别名配置先校验兼容性，统一使用已初始化的规范 Config。未取得可靠身份前不能以原始 Config 字符串或 Handle 字段名猜测。该契约的具体入口须在实现前设计并落实相应版本影响。
- Config 的普通数组与通道映射只要本行选择相同对象和相同槽位，应产生相同 DLL 请求和相同业务次数。保留原通道位置，Broadcast 仍以原通道1为源；映射语法不引入重编号或自动补源。单个显式槽位的普通/多通道选择仍须按下文待定项收敛，并在测试报告中记录实际路径。
- 本行选择多个不同对象时，首版按通道编号依次发普通请求；即使部分通道复用同一对象，也不悄悄合并成组或跨对象广播。这些案例归为跨实例路由测试，不能计入 DLL Sequential/Parallel/Broadcast 的通过证据。不同对象并发及共享资源互斥由外部测试驱动显式并发请求验证。
- 执行结果沿用现有控制台/标准输出，记录语句位置、实际调用路径、通道结果及清理错误。本轮不新增独立预期/报告文件或相关环境变量。请求已提交但未返回的结果标为未知，明确未提交的通道才标为未执行；空返回文本不直接标为跳过，不能填造成功结果。
- 业务次数、真实打开/关闭/析构、事务 begin/end 与实例身份由无硬件 DLL 夹具的查询方法及外部事件记录提供，不能以执行器自身循环次数充当 DLL 业务计数。增加针对性夹具及测试驱动，复用 tests/shared_runtime.rs、tools/verify_leased_node_dll.py、tools/verify_shared_resource_dll.py 的现有断言和独占文件模拟方式；不为测试新增生产 C 导出。

### 自动断言与预期错误

取消独立预期文件。需要的预期与断言只考虑在现有 .testflow 内表达；内联语法尚未经用户选择，不在本轮擅自确定，不新增用户维护的旁文件。实施该部分前先提供多个内联语法候选供用户选择。以下只保留断言的行为要求，不代表已确认具体写法。

- 预期至少包含 status 或 code，指定字段逐项精确匹配，output 按完整字符串数组比较，省略字段不凭消息文本推断。非 OK code 或非零 status 只有在明确预期且匹配时才允许作为成功测试步骤继续；未声明预期时保持成功响应要求。预期错误实际成功、错误类别不符、输出或观察值不符均使测试失败。旧 DLL 缺 code 时只能按实际 status 验证，不伪造稳定 code。
- 预期错误匹配后只继续后续语句，不重新执行失败步骤或继续其未开始的跨实例通道。部分初始化回滚仅清理本步新增对象，保留前置对象以便后续检查；初始化/对象状态按实际结果更新，不因预期匹配把失败对象标为已初始化。
- 业务计数、事件顺序、共享状态与清理失败由外部验证程序读取报告和夹具记录后断言。任何不匹配、宿主崩溃、超时或清理失败使整次验证非零退出；预期的关闭错误可以匹配，但仍需独立证明析构与资源释放完成，不能吞掉未预期的清理失败。
- 主失败与清理失败同时存在时均保留。未返回完整响应的故障和仍在执行的事务不得解释为“无副作用”；测试驱动须等待或显式处置宿主并核对外部记录后判定。

### 多宿主与故障编排

- 宿主编排由测试驱动负责，生成的 BAT 保持单宿主职责。至少一个宿主实际执行生成 BAT，其他持久宿主复用现有 Python C ABI 加载逻辑；通过明确的 ready、开始/完成、放行和退出握手交错初始化、调用与关闭，不能仅依赖 sleep 或启动多个顺序流程推断并发。
- 覆盖同进程加载原名/改名/独立编译 DLL，以及不同进程持有同一资源的情况。每个宿主/模块保持独立运行时及加载引用，直至显式关闭或进程退出。重复调用同一路径可能被操作系统复用模块，不能算独立 DLL；重复 InitDevice 复用本地对象也不增加租约引用。
- 自动节点 Lease 验证共享整个节点和业务状态；通信层 SharedResource 另设场景验证不同业务状态只共享物理连接。LocalLease 配置兼容、SharedResource 事务互斥、本地实例身份三者分别观察，不能互相替代。
- 并发场景使用夹具屏障和事件计数，验证真正同时在途的请求、实例完整调用互斥及完整事务 begin/end 不交错。不得把耗时变短作为唯一并发证据，也不要求 Parallel 在同一对象内部重叠执行业务。
- 分别终止资源所有者进程和配置租约服务宿主，验证不同的失效路径；注入发送后的超时/断连、业务错误、panic 和初始化失败。明确哪些客户端应永久失效、哪些仍可用，检查不自动重连、重放或回退 Direct，随后通过显式关闭和初始化恢复。
- 每次测试使用独立资源键、IPC 会话命名空间、报告和事件目录，设置有界握手/总执行截止时间。退出清理所有测试子进程；仍持有锁或加载引用时不删除租约锁文件、不覆盖 DLL。强杀只验证 OS 回收和存活引用行为，不声称执行了协作清理；模块卸载/保持引用的验证复用现有模块生命周期验证入口。

### 必须通过的验收矩阵

| 目标 | 场景与通过证据 |
| --- | --- |
| DLL 多通道执行 | Direct 与自动 Lease 分别覆盖 Sequential、Parallel、Broadcast；C ABI 实际批次调用1次，业务执行次数符合有效通道数；广播源有效时业务1次，源跳过时0次，输出按输入位置对齐 |
| 相同对象的 Config 表达等价 | 普通 Config、逐通道相同配置、集合/范围简写、可验证的身份别名产生等价批次；重复本地初始化不增加租约引用 |
| 跳过与错误语义 | 空槽位、非法参数数目、尾部默认值、通道1缺失/无效、广播源失败；注入业务执行错误验证 Sequential 首错后停止、Parallel 等待已接收项并保留其副作用且按位置返回首错；无法编码的场景单独验证拒绝或扩展协议，不计为未执行的成功覆盖 |
| 批次互斥与实例并发 | 多通道批次在执行期间，同一实例的另一请求不能插入；不同实例具备同时在途证据；Lease 模式下共享所有者的完整业务/事务仍互斥 |
| 跨实例 Config 路由 | 不同 Config/Handle 正确路由，缺配置/未初始化整行前拒绝，同键冲突不损坏原对象；明确该组不是 DLL 多通道策略证据 |
| 多 DLL/进程共享与最后引用 | 真正独立引用并发初始化只打开一次；共享状态；关闭非最后引用后其他引用仍可调用，最后引用才 close/drop/释放配置锁；新配置随后可重新打开 |
| 关闭参数及失败 | 仅最后关闭的 Input 到达所有者；关闭返回错误或 panic 后仍析构和释放资源，错误类别保真，可显式重建；外部事件证明完成，不能只看 CloseDevice 状态 |
| 兼容性与拒绝路径 | 相同资源不同配置、不同节点契约、不同完整 Init Input、不同事务协议等按实际版本的稳定错误契约拒绝；原所有者继续可用；Direct 不被静默切为 Lease 或反向回退 |
| 故障与恢复 | 所有者退出、租约服务退出、发送后超时/断连、业务 panic；验证受影响引用失效、未重放、配置仍受保护或按实际引用释放，显式关闭后才能重建 |
| 独立通信层代理 | 不同节点类型或 Handle 保留各自业务计数，底层连接仅打开一次；完整事务不交错，最后代理退出才释放；与自动 Lease 共享整个节点分开验收 |
| 宿主与交付 | Windows x64/x86 实际 BAT/PInvoke 与同架构辅助宿主执行上述直接受影响场景；现有流程中的断言、进程退出码和外部事件联合判定；既有 ABI 兼容和模块引用验证独立保留 |

tests/lease_resource_ownership.rs、tests/lease_final_close.rs、tests/lease_recovery.rs 及 features/lease/tests/shared_resource.rs 为现有行为基线，可复用场景与断言；其中 Rust 单元/多进程结果不冒充新 TestFlow 的 Windows DLL 端到端通过证据。新增矩阵全部待实施，不因现有脚本存在而标记已通过。

## 建议契约：仍须收敛后实施

1. 普通业务方法及 Config 的通道映射接收一个 JSON 对象，键采用上节已选的单通道/集合/范围形式，值为按 DLL 元数据顺序排列的字符串数组。拒绝非法键、重复或相交通道、非字符串参数、空对象及对象与旧位置参数混用。Delay 和框架固定查询保留原写法；初始化/关闭按当前配置模式处理，生命周期细节见 Config 章节。
2. 通道按展开后的编号定位，不按 JSON 属性书写顺序排列；省略的中间通道跳过。建议结果范围为 ch1 到展开后的最大显式编号，最高编号须在展开范围和分配槽位前检查容量，避免稀疏大编号或巨大范围导致无界分配。是否允许显式 null 保留尾部跳过位置、容量的来源与数值，均待确定，不把表格的六列硬编码为框架上限。
3. 旧字符串参数形式建议继续作为普通单通道调用。新对象仅含 ch1 时，是否也走普通单通道入口，或始终表示多通道请求，尚待决定；只有 ch3 时须保留前两个槽位，不能把它压缩成普通调用。此选择影响未声明 instance 节点是否接受对象单通道形式。
4. 建议支持多行调用及独立注释行。收集完整语句须识别 JSON 字符串与转义，不以字符串内的括号结束语句；保留起止行号，在 Rust 检查器与 Windows PowerShell 5.1 执行器中保持一致。JSON 对象不引入尾逗号、行内注释或其他非标准扩展。
5. 框架的一次多通道请求只使用一份 Config 定位一个对象。同一对象的多个通道统一进入真实 DLL 多通道路径，Sequential、Parallel、Broadcast 沿用框架，不在语法中再指定；Parallel 不承诺同对象业务重叠，Broadcast 固定执行通道1一次，源通道跳过则整批跳过。不同对象才按上述跨实例规则派发；跨实例并行由验证驱动显式组织，不由范围键隐式开启。
6. 参数包含逗号、首尾空白、空字符串、零参数通道 [] 时，同一对象路径的当前 TB 多通道编码不能完整表达其语义。实施前比较“首版明确拒绝不能表达的值”与“同步扩展平台协议”，确定范围及版本影响；禁止静默改值、将 [] 当跳过，或增加只有工具理解的转义。跨实例路径的普通请求不经过通道内逗号拼接，不应无依据沿用该编码限制；仍按实际节点参数契约校验。batch/encoding 仍按实际方法元数据提供的槽位传入。默认值与参数数量错误采用工具预检还是保留框架跳过规则，也须明确；不能在广播非源通道上擅自增加业务类型解析。
7. 输出按通道编号显示原始文本；不能把空返回值直接标记为跳过，也不能用逗号再次切分字段。自动断言、预期错误和执行报告按测试设计章节纳入首版；表格输出变量绑定与表达式求值不因此自动新增。
8. 不支持多通道或独立多实例的节点、非 TB 默认平台及旧 ABI 的实际兼容范围须明确检测或限制方式；当前元数据不能证明的能力不可凭显示名称推断。运行错误保留 status/code/message 和已有通道上下文，不自动重试或声称其他通道未执行；退出在现有自动关闭机制上增加所需的每通道绑定与对象生命周期记录，不另建资源代理所有者。
