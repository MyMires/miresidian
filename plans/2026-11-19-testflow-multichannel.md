## 一、语法与边界

```text
发送数据("AA", "HEX")
发送数据({"ch1": ["AA", "HEX"]})
发送数据({"ch1,ch3,ch5": ["AA", "HEX"]})
发送数据({"ch1-ch6": ["AA", "HEX"]})
发送数据({"ch1": ["AA", "HEX"], "ch2": null, "ch3": ["BB", "HEX"]})
```

- 键只支持 chN、逗号连接的 chN 集合或一个包含端点的 chN-chM 范围。N 为无前导零正整数，键内无空白，N <= M；不增加通配符、范围与集合混合或变量表达式。
- 输入值为字符串数组；业务及初始化/关闭 Input 对象允许 null，表示显式跳过。Config 对象不允许 null。拒绝空对象、重复 JSON 键、相交通道及参数中的数字/嵌套对象，不按后写覆盖。
- 通道按数字编号定位，结果范围从 ch1 到最大显式编号，包含尾部 null；省略的中间位置跳过，不压缩或重编号。工具固定上限256，编号和范围端点在展开前检查；DLL 更低的自身限额由其实际响应处理并展示，不假装已通过能力查询获知。
- 普通业务参数形式等价于 ch1；只有 ch1 且为数组的对象也走普通请求。最高编号大于1时使用下面明确的批次或跨实例规则。单 ch1:null 为跳过、不调用 DLL；无实际调用不能附带 status/code 预期。
- 支持多行完整语句及独立 #、// 注释行；JSON 内不增加尾逗号、行内注释。识别字符串/转义、括号/数组/对象配对和调用后的 =>，字符串内的 => 不作分隔。保留起止行号；Rust 和 PowerShell 在字典转换前检查重复键，以相同正反例验证一致性。
- Config、Delay 是工具指令，不接受 DLL 响应预期。Delay 沿用现有毫秒字符串范围。其余固定查询与业务方法使用现有 DLL 契约，预期绑定该调用本身，不靠步骤编号或旁文件关联。

## 二、配置、初始化和关闭

```text
# 全部通道共用配置
Config("COM1", "115200")
InitDevice()
发送数据({"ch1-ch3": ["AA", "HEX"]})
CloseDevice()

# 每通道配置、初始化 Input 和关闭 Input
Config({"ch1": ["COM1", "115200"], "ch2": ["COM2", "9600"]})
InitDevice({"ch1": ["启动A"], "ch2": ["启动B"]})
发送数据({"ch1-ch2": ["AA", "HEX"]})
CloseDevice({"ch1": ["关闭A"], "ch2": ["关闭B"]})

# 相同配置使用相同选择器
Config({"ch1-ch6": ["COM1", "115200"]})
```

示例参数仅说明语法；实际数量与顺序按被测 DLL 填写，不代表串口节点只有两个 Config 参数。

- Config 只选择配置；普通形式设置共用模式，对象形式完整替换当前通道映射。整条配置验证成功后替换，切换选择不隐式初始化或关闭对象。不在新映射中保留旧通道默认值。
- 保留现有 GetInitConfig 与尾部配置补齐方式；工具分组依据是补齐后的完整字符串数组逐项相等。不额外做数值、大小写、前缀或地址别名归一化，不猜实例键/Handle 位置，不将不同文本宣称为独立对象或同一对象。
- InitDevice()/CloseDevice() 的普通参数，包括空参数，作用于当前选择的全部配置；共用模式只需一次调用。对象 Input 只选择显式非 null 通道，按编号派发；共用模式允许各通道使用同一份 Config。缺少对应 Config 的非 null 通道整行前报错。
- 同一条初始化/关闭语句中，完整 Config 相同且 Input 相同只调用一次，结果关联至所有选中别名；相同 Config 对应不同初始化或关闭 Input 时，在任何该行 DLL 调用前拒绝，避免顺序覆盖。不同 Config 依次调用；不承诺跨配置原子性。
- 初始化 Input 通过现有独立 input 数组原样传入。GetFunctions 的 InitDevice 描述包含 Config 时先剥离 GetInitConfig 对应的配置部分，不把 Config 重复传入 Input。关闭元数据不完整时不猜测关闭参数数量，原样透传，由 DLL 返回实际错误。
- 记录每份完整 Config 的成功初始化请求和成功关闭请求，作为工具流程顺序检查；成功初始化响应不等于对象创建证明（空身份可能被 DLL 跳过）。实际复用、配置冲突、Handle 和实例数量策略均由 DLL 决定，业务仍可能返回未初始化或未知对象，必须展示并按预期处理。
- 多个独立 Config 场景要求被测 DLL 本身支持多实例，这是被测节点的使用前提，工具无法从现有文本签名可靠探测。默认单实例可能替换旧对象，不能把若干成功 InitDevice 当成多实例已成立；专门测试用对象地址/计数输出验证实际行为。不增加框架接口来补探测。
- 相同对象应统一使用相同 Config 文本。不同文本是否被 DLL 归一到同一对象不由工具合并；显式关闭别名后其他别名可能失效，随后按 DLL 真实响应处理，不能以工具状态表证明对象仍存活。

## 三、运行时所有权与失败清理

- 每个 BAT 使用独立宿主进程和该流程独占的 DLL 本地运行时；不支持把流程接入同一运行时中未知外部调用者已打开的对象。跨 DLL/进程租约共享仍允许，其他宿主的本地运行时独立。
- 取消“必须识别原子创建回执、只回滚本步新对象、按实例代次关闭”的旧要求：现有接口没有这些信息，不能编造。跨 Config 初始化允许部分成功，不宣称事务回滚。
- 任何意外执行错误或断言失败：显示实际结果，停止后续流程，进入 finally，以空 Config/Input 调用现有 CloseAllDevices，尽力清理本宿主全部本地对象。显式 CloseDevice 保留选定范围和调用者参数；显式 CloseAllDevices 保留全局语义。
- 匹配明确的预期错误时允许下一语句检查或显式恢复，不重试失败语句、不继续其未开始的跨实例通道；部分初始化已经成功的对象保留到显式关闭或最终清理，输出中明确这一事实。
- 最终 CloseAllDevices 即使此前显式关闭过也可调用；保持其幂等语义，避免按 Config 别名重复清理同一对象。它只释放本地对象/代理，其他宿主持有的租约引用不受工具强行关闭。
- 自动清理用空 Input，业务需要关闭参数时由流程显式 CloseDevice(...) 提供；自动清理不保证设备完成业务复位。清理失败保留实际错误并使宿主非零退出，不覆盖原失败，也不声称资源已经全部释放。全部清理调用及实际结果始终输出。
- 强制终止不保证 finally；相应测试只验证进程退出、OS 回收和其他引用的实际行为。执行状态、已知未提交、已提交但结果未知分别展示，不把未知结果填成成功或未执行。

## 四、使用现有 DLL 接口派发

- ABI 10 的对象流程统一使用已存在的 platform:1（TB）及单 JSON miresidian_invoke 入口，包括元数据和生命周期，避免猜测 DLL 默认平台。原字符串流程保留默认平台行为。ABI 7–9 保留原三参数入口，对象流程要求 DLL 已采用 TB 默认契约；不宣称支持任意自定义平台。
- 普通业务调用使用 ch1 对应 Config；映射模式缺少 ch1 时明确报错，不默选其他通道。对象输入中只有 ch1 数组时也走普通请求，零参数 [] 可以原样调用。
- 本行全部非 null 通道的完整 Config 相同时，且最大显式编号大于1：发一次既有 TB 多通道请求。input 为“共享”标记加各通道参数用英文逗号连接后的字符串；null/省略槽位为空字符串。保留全局位置，通道1缺失时不补源。不能宿主循环普通请求来冒充 DLL 批次。
- 共用 Config 下多个全 null 槽位仍发送真实 DLL 批次，验证整批跳过；映射 Config 下全部 null 为无调用跳过语句。后者无实际总体 status/code，不能对其写响应预期。
- 本行非 null 通道具有不同完整 Config 时，按通道编号分别发送普通请求，即使其中部分配置重复也不隐式组批。结果回填原通道，首个失败停止后续未开始通道。这类场景只证明跨 Config 路由，不算 DLL Parallel/Broadcast 覆盖。
- 真正 DLL 批次沿用节点的 Sequential/Parallel/Broadcast。执行策略固定时不增加选择项，可选策略由已有 Config 选择；工具不从文本名称推断策略，不把相同参数的范围键当广播。Parallel 不要求同对象业务重叠，Broadcast 仍只执行原通道1一次。
- 批次 Input 中数组为空、参数含英文逗号、空字符串或需保留的首尾空白，工具在该行调用前明确拒绝：现有 TB 不能无损表达这些值。普通请求/跨 Config 普通请求不经过逗号编码，按 DLL 原契约传入。单通道普通 Input 首项恰为 TB 保留标记“共享”时明确拒绝，不能意外转成批次。
- 参数个数错误等可被 TB 正确编码的输入允许到达 DLL，以验证其既有跳过/错误规则；不对业务 Input 自动补值或过滤槽位。缺失尾部框架默认值仍交给 DLL。现有接口不能表达的结构化零参数批次不计为工具已支持，也不修改协议绕过。

## 五、执行结果和内联断言


已选择方案 A：方法调用后使用 => 附带一个 JSON 预期对象。调用与预期属于同一条完整语句，支持多行；无需独立预期/报告文件，也不增加调用前的 Expect 指令。

模式按每条调用区分，同一流程可以混用：

| 写法 | 模式 | 输出与处理 |
| --- | --- | --- |
| 方法调用，无 => | 执行模式 | 调用 DLL 并展示完整实际结果，不比较预期，不生成断言通过/失败结论；DLL 报错按执行失败处理 |
| 方法调用 => 预期 | 断言模式 | 同样先展示完整实际结果，再展示已声明的预期与比较结论；不匹配时列出预期/实际差异及对应通道/返回参数 |

实际输出不能被“执行成功”或“断言通过”一行替代。普通请求拿到多个独立返回参数时展示其完整数组；DLL 多通道只返回 TB 拼接文本时展示各通道原文，不能为了显示多个参数而猜测拆分。断言只检查 code 时，也仍然展示未参与比较的实际 output。

```text
# 执行模式：展示实际返回数据，不作预期断言
测量("直流")

# 只检查整次调用成功
发送数据({"ch1-ch2": ["AA", "HEX"]}) => {"code": "OK"}

# 分别检查各通道的返回文本
读取数据({"ch1-ch3": ["HEX", "Length", "00", "2", "1000"]}) => {
    "code": "OK",
    "output": {
        "ch1,ch3": "01 02",
        "ch2": "03 04"
    }
}

# 多个通道使用相同输出预期
读取数据({"ch1-ch6": ["HEX", "Length", "00", "2", "1000"]}) => {
    "code": "OK",
    "output": {"ch1-ch6": "01 02"}
}

# 预期错误必须在发起 DLL 调用前解析，匹配后才继续后续语句
发送数据({"ch1": ["AA", "不支持的格式"]}) => {"code": "INVALID_ARGUMENT"}

# 假设测量方法依次返回电压、电流、状态；下面均为语法示例
# 普通单通道：完整的多个返回参数
测量("直流") => {
    "code": "OK",
    "output": ["12.0", "0.5", "正常"]
}

# 多通道：各通道分别提供多个返回参数，数组顺序对应方法的 Output 顺序
测量({"ch1-ch2": ["直流"]}) => {
    "code": "OK",
    "output": {
        "ch1": ["12.0", "0.5", "正常"],
        "ch2": ["11.9", "0.6", "正常"]
    }
}
```

- => 仅在 JSON 字符串之外、调用结束后识别；参数或预期字符串中的同样文本不作分隔符。检查器与执行器必须在执行调用前解析并验证整条语句，包括多行预期。重复分隔符、残缺 JSON、未知字段、重复字段或错误类型均报告原语句行号。
- 预期对象允许 status（整数）、code（字符串）与 output，至少包含 status 或 code。不写 => 时是执行模式，不是隐式断言模式：展示实际返回数据，但不判断其是否符合业务预期。执行状态仍按 DLL 返回处理，status 非零或实际 code 表示失败时停止并清理；旧 DLL 缺 code 时使用实际 status，不合成 code。该状态处理用于识别调用错误，不计为一次预期断言。按 DLL 规则跳过通道也可能整体成功，不能据此声称每个通道都执行业务。status/code 预期检查整次 DLL 调用，不能在 DLL 只返回总体错误时虚构各通道错误码。
- 多通道 output 采用 JSON 对象，键与输入相同，支持 chN、chN,chM 和 chN-chM；值可为通道完整返回文本字符串，或按方法 Output 顺序排列的字符串数组，后者表达多个返回参数。同样支持如 {"ch1-ch6": ["12.0", "0.5", "正常"]} 的相同多参数预期。只检查列出的通道，重复/相交选择报错，不使用属性顺序覆盖。预期引用超出本次槽位范围或没有实际返回结果的通道时明确失败，不能补造空值。DLL 已返回的 TB 空槽位可以按空文本比较；跨实例尚未派发或 null 跳过且没有响应的通道不能伪造输出。
- 普通请求的原始 output 数组可按数量、位置和文本逐项精确比较，包括跨实例请求中已保留的每通道完整数组。通道预期为字符串时，按 TB 槽位规则用英文逗号连接实际输出后作文本比较。
- DLL 多通道路径只返回现有 TB 槽位文本；字符串预期与原文比较，数组预期先按同一 TB 规则用英文逗号连接后比较，不能对实际文本反向猜测字段。此路径的数组写法方便表达多个参数，但不宣称无损的字段级断言：字段自身含逗号时可能存在边界歧义，诊断必须明确本次是 TB 编码文本比较。该限制不以修改框架或 ABI 绕过。空文本可以作为预期，但匹配空文本不证明业务执行或通道跳过，执行次数仍须独立验证。
- 对一次普通 DLL 请求，也可使用 output 字符串数组精确比较原始完整输出；跨实例语句使用通道映射，避免把多次响应误当成单次 DLL 输出数组。跨实例按编号派发，首个失败请求的 status/code 作为整句失败，后续通道不再执行。

- 断言模式下，所有已指定预期逐项精确匹配，省略字段不凭消息文本推断。非 OK code 或非零 status 只有在明确预期且匹配时才允许继续；此时分别显示“实际执行失败”和“符合预期，断言通过”，不能把实际错误显示为执行成功。预期错误实际成功、错误类别不符、输出或观察值不符均使测试失败。旧 DLL 缺 code 时只能按实际 status 验证，不伪造稳定 code。
- 预期错误匹配后只继续后续语句，不重新执行失败步骤或继续其未开始的跨实例通道。初始化部分成功时不宣称具备逐对象回滚回执：匹配预期错误后保留实际已成功请求，允许后续检查或显式关闭，最终由本宿主的 CloseAllDevices 清理；不因预期匹配把失败初始化标为成功，也不把成功响应当成创建证明。
- 业务计数、事件顺序、共享状态与清理失败由外部验证程序读取报告和夹具记录后断言。任何不匹配、宿主崩溃、超时或清理失败使整次验证非零退出；预期的关闭错误可以匹配，但仍需独立证明析构与资源释放完成，不能吞掉未预期的清理失败。
- 主失败与清理失败同时存在时均保留。未返回完整响应的故障和仍在执行的事务不得解释为“无副作用”；测试驱动须等待或显式处置宿主并核对外部记录后判定。


## 六、DLL 多通道与租约验证

验证复用现有 DLL 脚本和 TestFlow 自身测试入口；不得修改框架或宏来制造测试能力。缺少策略组合夹具时，在工具测试的临时目录生成独立节点，使用实施时核实的 crates.io 精确已发布框架依赖；禁止 path/git/patch 覆盖，不把临时夹具作为用户新增维护文件。

- 至少一个宿主真实执行新生成的 BAT；其他宿主复用已有 Python C ABI 调用。保留原名、改名、独立编译模块和跨进程场景；重复加载同一路径可能共享模块，不能当独立引用。
- 控制器使用现有脚本中的线程/子进程能力，新增逻辑限于工具自身验证范围；不新增业务流程的宿主指令或配置文件。用明确 ready/entered/release/completed 事件同步，不靠 sleep 推断并发。

- 自动 Lease 共享整个节点与状态；SharedResource 验证独立业务状态只共享连接；LocalLease 配置保护分别验证。重复本地 InitDevice 不增加引用，不能充当最后引用关闭测试。
- 用既有文件锁/打开关闭计数/事务事件证明物理打开次数、close/drop 顺序及不交错。普通对象编号和租约资源身份不混用；工具调用次数不能替代实际业务计数。
