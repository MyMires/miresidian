# Miresidian Node 项目开发

目标是完成符合 Miresidian 契约、实现真实业务且有相应验证证据的 Node 项目。依据用户任务选择所需阶段；修改已有节点时围绕改动推进，不重复初始化和整套开发流程。

## 1. 明确节点要完成的业务

读取目标项目的 AGENTS.md、适用规范、现有源码及调用说明；新建节点或修改生产代码、测试前，必须读取并执行 [Node 项目规范](references/project-standards.md)，明确本次模块职责、依赖方向和测试归属。从用户需求、目标资源资料和已有实现中确认：

- 节点负责的目标资源或业务、通信方式，以及需要支持的操作和预期输出。
- 初始化需要的连接配置、资源身份、默认值与单位；每次操作独立传入的业务输入。
- 连接建立、请求响应、超时、资源错误和资源释放的实际规则。
- 单实例是否足够，是否确实需要同时管理多个节点实例、共享资源、多通道调用，或将同一操作按一组数值或 format 记录顺序重复执行。
- 本次交付目标：项目源码、可运行节点、DLL 发布包，以及要求的平台/位数和硬件验收条件。

已有项目优先保留其契约和依赖选择。对影响协议正确性或公开行为的缺失信息，先查现有资料，再询问必要问题；可以并行推进不依赖这些答案的实现。不能猜测目标协议或以示例回显冒充业务完成。

## 2. 把业务需求落实为节点契约

在实现前读取 [节点设计与实现约束](references/node-contract.md)。将需求映射到实际节点的方法、参数和状态，复杂度需要时用一张简表记录操作、Config、Input、Output 及错误条件；已有调用说明可直接承担此职责。

- 确定节点名称和业务对象身份。存在业务初始化配置时，把连接地址、端口或资源标识等主键放在 Config[0]，其余配置写明默认值、单位与有效范围。
- 明确初始化返回什么、每个业务方法需要什么输入、输出什么，以及何时报告参数错误、超时、资源失败或未初始化。
- 对有限离散取值的 Config/Input，必须按 [完整选项与内部枚举规则](references/node-contract.md#有限取值必须声明完整选项) 声明全部实际支持的选项，不能只给默认值；Rust 业务内部优先使用枚举，转换归业务模块，选项、默认值与实际支持范围保持一致。
- 根据目标资源的使用方式确定实例和资源所有权；有多实例、多通道或租约需求时，核实所选已发布框架的支持方式，再显式声明。
- 选择框架 features 是节点设计的一部分：按 [框架能力与 features](references/features.md) 将需求落实到依赖配置、节点声明/参数标记和验收行为。明确默认单实例是否足够、是否需要 instances、lease、batch 或显式 format，以及它们是否组合；不能只开 feature 而遗漏对应标记，也不能默认启用全部能力。format 与 batch 可独立使用，基础示例只开启本次所需能力，组合用法另列。
- 划清节点业务、资源协议、通信传输与框架生成代码的职责。业务节点使用宏声明契约，框架负责平台描述、调度和 ABI。
- 新增或改变公开行为时同步调整调用说明和验证目标；不为局部功能重设计整个节点。

这一步的结果应能直接指导代码和验收，不为简单任务额外建立设计文档体系。

### 构建项目的方案确认门禁

新建或构建 Node 项目时，必须在编写任何业务代码之前整理方案和实施计划，提交给用户并等待明确确认。方案至少说明节点职责、操作及 Config/Input/Output 契约、通信和资源生命周期、所选框架 features、主要错误处理，以及验证和交付范围；实施计划列出主要步骤和依赖。按项目复杂度控制篇幅，确认可在对话中完成，不强制新建文档。

方案尽量附带 UML 类图，展示节点状态、主要业务对象、通信或协议组件及其关系；可用 Mermaid classDiagram 在对话中表达。简单项目或现有信息不足以确定结构时，可简要说明并用文字描述，不为凑图臆造类或关系。

项目模板初始化可以在确认前或确认后进行，但初始化不代表方案已获确认；确认前不得编写或修改业务实现。用户提出调整时先更新方案和计划，再等待确认；未获得明确确认时停止在此门禁。已有节点的局部维护仍按任务范围处理，不因此强制完整项目方案流程。

## 3. 建立或完善项目结构

新项目使用现有节点模板作为起点；模板只有无硬件回显，生成成功只是项目起点。已有项目直接在原结构中修改。

项目应具备独立 Cargo 配置和真实锁文件、节点源码、节点调用说明、与业务一致的烟测及修订记录。只依赖 crates.io 已发布框架的精确版本；保留已有精确版本，除非任务确实需要升级。不得用 path/git、本地覆盖或伪造锁文件绕过发布要求。

把选定的框架 features 写入节点 Cargo.toml，使正常构建、测试及交付使用同一能力配置；若项目确需自身的可选 feature，显式转发依赖 feature 并保证交付路径启用。同步记录对实例关联、Config 布局和资源访问行为的影响。

按 [Node 项目规范的目录结构](references/project-standards.md#项目目录结构) 确定基础文件、按需模块与测试位置；[node.rs 优先保持契约可读性](references/project-standards.md#noders-契约可读性)，只放宏标记的节点结构体和契约方法及必需的 use/impl、对象字段和契约注释，集中展示操作、参数、输出标注，方法体仅做简短委托与直接映射，设备状态、检查和业务流程交由业务对象管理。禁止在 node.rs 添加未标记的手写辅助方法/函数、辅助类型、常量定义或测试模块，或通过额外 impl、闭包及本地宏保留被操作调用的业务子逻辑；交付前须枚举文件内实现并核对本次调用链归属。普通业务模块的单元测试允许内联，不把文件行数、目录数量或测试外置当作结构改善的证据。

需要创建模板、安装工具或准备目标环境时才查阅 [工具操作参考](references/commands.md)。不把工具升级、完整环境配置或框架修改作为每个 Node 任务的前置步骤。

## 4. 实现真实业务和完整生命周期

以需求中的一条完整调用链推进：构造配置 → 建立连接 → 执行业务 → 返回结果 → 关闭资源，再补齐本次需求涉及的其他操作及失败路径。

- 初始化验证配置并取得资源；只有构造成功才交给框架持有，部分失败时释放已取得的资源。
- 业务方法实现真实协议和结果转换，明确响应边界、超时、资源错误与状态变化。请求和响应需要原子性时，保持完整事务互斥。
- 关闭方法释放连接、会话和临时资源，必要时由 Drop 兜底；明确关闭失败和后续再次使用的行为。
- 用 MiresidianResult 表达预期错误，不用 panic 处理正常失败，不把通信失败包装成成功的默认业务值。不对有副作用的操作无依据地自动重试。
- 使用框架已有的参数、输出和跨语言编解码能力，不在业务节点重写平台分发、函数列表、初始化描述或 DLL 导出。
- 在配置来源、单位、协议限制、状态转换和清理责任等关键位置补充注释；说明真实约束，不保留与最终业务不符的模板注释。

同时维护节点文档和烟测：操作名、参数顺序、默认值、输出含义与调用顺序须和最终源码一致。模拟实现或目标资源尚未接入的部分明确标识，不能当成真实能力交付。

## 5. 用相应证据验证本次交付

实现前或改动明确后，按 [节点验证与验收](references/verification.md) 选择能证明本次行为的最小有效验证集合，遵守目标仓库的强制门禁。交付前必须完成 [项目规范的执行与审查](references/project-standards.md#交付前执行与审查)，对职责、依赖、拆分收益、测试质量和实际检查结果给出依据；相关违规未修复时不得声称完成。

重点回答：配置和参数是否正确、方法是否被框架注册、业务是否符合协议、生命周期是否释放资源，以及交付 DLL 能否在要求的环境加载调用。测试针对这些行为，而不是仅确认工具能启动或文件存在。

没有目标资源时通过协议样本、模拟响应和资源状态验证可证明的部分；真实通信与资源行为保留为明确的未验证范围。只验证本次要求的平台与位数，不默认扩展到所有项目、框架或工具。

复用仍然有效的已通过结果；修复后先重跑失败项和直接受影响项。耗时检查提前说明目的和预计耗时，超出预估时重新评估剩余必要性。满足验收条件后结束，不因无关失败继续扩展范围。

## 6. 完成交付

交付源码时，提供完整实现、必要注释、节点调用说明、业务验证及明确的环境要求。交付 DLL 时，还须有本次目标产物、对应头文件、版本/架构/摘要清单和可执行的调用示例；打包操作按需查阅工具子文档。

按目标项目规范同步自身版本、锁文件和带日期的 CHANGELOG；框架、节点与工具独立编号，不因节点变更升级无关组件。提交、标签和在线发布依用户任务及仓库要求执行。

向用户报告已实现的业务、项目版本和产物位置、实际验证结论，以及未完成或未验证的事项。区分结构检查、编译、打包、DLL 加载、无目标资源测试和真实资源测试，不跨层声称完成。

框架升级默认不修改、升级或重新打包已有 Node 项目；只有用户明确要求迁移时才更新节点依赖和锁文件。
