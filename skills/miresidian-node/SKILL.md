# Miresidian Node 项目开发

围绕真实业务完成 Node 项目。新建和更新都必须先形成方案文件，再严格按文件实施；已有节点沿用适用的结构、契约和依赖。禁止跳过方案直接编码、初始化模板或升级依赖。

本 skill 提供开发流程、关键决策和完成条件。框架与工具的具体 API、命令、兼容性及规范从对应版本的官方资料取得；skill 不声明固定适配版本，不要求项目跟随 skill 或最新发行升级。

## 1. 先形成方案文件，再实施

读取目标项目的 AGENTS.md、README、调用说明及相关源码，确认业务操作、协议依据、配置、对象身份、目标平台和交付范围。业务与资源资料不完整时先查证，影响正确性的缺口再询问，不猜测设备协议。

所有 Node 新建、更新、缺陷修复、局部维护、重构、依赖/构建/交付调整都必须先在目标项目新建或更新任务方案文件，再实施。默认使用 plans/YYYY-MM-DD-主题.md；沿用项目既有方案目录。新项目尚无目录时先在工作区约定目录落盘，并写明目标项目和最终归档位置。不得先运行模板初始化再补方案，小改动可用短方案但不能豁免文件。

方案必须明确目标/非目标、现状与实际版本、具体实现方式和职责、Config/Input/Output、资源所有权/共享状态/生命周期、失败与并发边界、影响文件、版本/文档/交付影响、实施顺序及验收证据。写方案前只做只读调研和资料查证；关键资料缺口先解决，不在编码时猜测。按[方案文件与实施约束](references/planning.md)落实内容及门禁。

向用户说明文件路径、设计要点与执行条件。新建或整体构建 Node 项目必须在实施前取得方案确认；已有确认/授权涵盖本次具体方案时记录依据并继续，不重复确认。用户要求先审方案时必须等待，不能用一般性任务授权或沉默代替确认。方案文件不自动授权发布、部署或其他外部操作。

实现方式必须严格遵循文件中的设计、接口、资源边界和步骤。发现需要调整时先停止受影响步骤、更新方案并说明原因及影响，满足必要确认条件后再实施；严禁先改代码后补计划或事后反写方案掩盖偏离。实施和交付逐项对应“需求 → 设计 → 代码/步骤 → 验证证据”，未完成或未验证项如实记录。

## 2. 确定版本并查阅官方资料

先识别目标 Node 自身版本、实际依赖的框架版本、解析到的组件及启用能力，依据 Cargo.toml、Cargo.lock 和 Cargo 解析结果；工具独立核对已安装版本，不从框架版本推算工具、ABI 或协议版本。新项目先确认所选版本已发布，再用 Cargo 生成真实锁文件。

维护已有 Node 时，以该节点当前源码、调用说明及对应发布记录确定业务契约，保留适用依赖，不套用新模板或其他节点的行为。同一仓库、工作区或任务包含多个节点、框架版本时，分别按目标包及其实际解析结果核对依赖、能力和资料，不以仓库根版本或另一个节点代表全部项目。跨节点/DLL 协作须另核对 ABI、通信和资源共享协议兼容性，不因同属 Miresidian 就假定互通。

以下入口用于发现官方资料，进入后选择实际使用的精确版本：

| 资料 | 官方入口与用途 |
| --- | --- |
| 框架发行 | [crates.io](https://crates.io/crates/miresidian)：确认可用版本、包说明和仓库信息 |
| Rust API | [docs.rs](https://docs.rs/miresidian)：切换到依赖版本后查 API、类型与 feature；首页可能跳转 latest |
| 开发手册、专题与示例 | [官方仓库](https://github.com/MyMires/miresidian)：在对应发布标签或已核实的发布提交中，从文档中心查节点开发、能力、ABI 和示例 |
| 工具 | [CLI](https://crates.io/crates/miresidian_cli)、[Pack](https://crates.io/crates/miresidian_pack)、[Windows TestFlow](https://crates.io/crates/miresidian_testflow_windows)：按各自实际版本查包说明、发布源码及工具文档 |

- 设计时查所需能力与约束，实现前确认相关 API、声明和调用布局，初始化或交付前查工具用法；只读取本次涉及的资料，复用已确认且仍有效的结果。
- 在线文档必须核对版本与来源；不将搜索摘要、master/latest 或其他版本的示例直接作为当前契约。仓库标签与 crate 版本分别核对，工具文档不能仅按根框架标签选择。
- 文档缺失时查对应发布包中的 README、示例、Rustdoc 和源码；可通过发布包的源码修订信息定位仓库提交，不猜标签。具体命令在执行前再核对实际程序的版本与帮助。
- 已有完整且版本匹配的资料可直接复用；无法联网时使用同版本本地资料。明确关键资料缺口及其影响，在无法确认的能力上暂停依赖该结论的实现，继续其他有依据的工作，不擅自升级或用本地框架替代已发布依赖。
- 记录本次实际采用的资料版本与入口，便于复核；不为此额外建立常驻版本表、文档副本或报告文件。官方技术资料用于确认契约，项目范围与执行约束遵循用户要求及项目规则。

### 构建前展示 features 并由用户选择

新建或整体构建 Node、调整 feature 组合前，按目标项目及其实际依赖版本，向用户展示支持的 features 与功能配置清单。依据项目 Cargo.toml、Cargo.lock、解析结果及对应版本官方资料，覆盖 Node 自身声明的 features，以及实际框架/直接依赖向该 Node 提供的可选能力；区分项目开关与依赖开关，不把依赖全部传递特性都当作用户选项。新项目从拟采用的已发布版本及模板资料只读查证，不为列清单先初始化项目，也不照搬最新版本的能力表。

用便于比较的表格列出各项：feature 名称与所属包/版本、功能与适用场景、默认是否启用、当前项目实际是否启用、启用/关闭方式、关联配置及默认值，以及依赖、互斥或组合约束和平台/交付影响。编译开关与节点声明、运行时 Config/Input 分别说明；不能仅启用 feature 就声称业务已接入。配置细节仅覆盖该能力实际需要的内容，未查证的支持范围或默认值明确标为待核实。

给出符合业务需求的推荐组合和理由，明确请用户选择保留、启用或关闭哪些项，以及仍需决定的配置。选择可以与方案确认一并完成；未选择时保持待确认，不把默认项、推荐或沉默当作同意，不执行依赖该选择的模板初始化、依赖修改或构建。已有明确选择/授权覆盖当前版本、目标与组合时记录依据并复用；局部维护保留已确认组合，不要求每次小修复重选。项目没有可选 feature 时说明事实及固定能力，不虚构选项。

把所选组合、是否保留默认 features、关联配置及验收范围写入方案，并落实到项目依赖、节点实现、构建/打包参数和调用说明。验证实际启用结果与选择一致；不能只在临时检查命令中打开。多个 Node 或不同依赖版本分别列清单和记录选择，交付时报告实际组合及验证边界。

## 3. 严格按方案实现契约与业务

开始每一步前核对方案中的设计、目标文件、前置条件和验收项。明确操作、参数来源与顺序、选项、单位、缺失/空值、输出和错误条件，核对对应版本的生命周期入口及框架生成职责。按需要选择多实例、多通道、配置协调、物理资源共享、批量调用或格式转换，并落实实际依赖配置、节点声明或通信层接入；避免预先开启全部能力。

参数声明及预填要求查官方仓库现行节点开发手册的“参数声明规范”，按[契约检查](references/review.md#契约与输入输出)验收；API、解析及运行行为仍按项目实际依赖版本核对，skill 不另行维护技术规则。

区分业务对象身份、配置兼容性与物理资源所有权。共享独占连接时明确资源身份、通信提供者、完整请求—响应事务、关闭引用和故障边界，不能用兼容租约登记成功证明连接已共享。

独立节点只依赖 crates.io 已发布的框架精确版本，锁文件由 Cargo 生成；禁止框架 path/git 依赖及 patch/replace/paths 等本地覆盖。框架尚未发布时明确依赖阻塞；框架或工具升级必须属于任务范围。

新项目按官方工具文档初始化，已有项目保留适用结构。契约模块集中声明节点和平台方法并委托业务；业务、校验、协议与资源管理归所属模块。优先复用框架、标准库和适用依赖，按真实职责拆分，具体审查见 [开发与交付检查](references/review.md)。

先完成“验证配置 → 建立资源 → 执行业务 → 返回结果 → 关闭资源”的调用链，再补齐其他操作和失败清理。实现真实协议、超时及生命周期，同步调用说明、必要注释和业务烟测；模板回显与模拟能力明确标识。

## 4. 验证本次行为

按方案中的验收矩阵和 [开发与交付检查](references/review.md) 选择与改动相关的检查，完成项目门禁和所选能力的验收；预期行为以本次查证的版本契约及业务要求为依据。

复用仍有效的验证结果，修复后先重跑失败项与直接受影响项。耗时检查先说明目的和预计耗时，超出预估时重新评估范围。无目标资源时验证协议样本、模拟响应和资源状态，明确真实通信未验证；取得本次平台、位数和能力所需证据后结束。

## 5. 完成交付

按项目规则同步自身版本、真实锁文件、带日期的 CHANGELOG 和调用说明。DLL 交付提供目标产物、对应头文件、版本/架构/SHA-256 清单及可执行示例，并取得目标平台的实际加载调用证据。

交付目录及依赖加载要求查对应版本的开发规范与工具说明，并按[交付检查](references/review.md#验证与交付)验收。

交付前在方案文件逐项记录实施状态与验收证据、偏离及其修订依据。报告方案路径、已实现业务、Node 与框架/工具版本、产物位置、实际验证和剩余事项，分别说明模拟、DLL 调用与真实资源结果。提交、标签和发布依用户授权及项目规则执行；框架、节点、工具和 skill 各按实际变化维护，不相互触发无关升级。
