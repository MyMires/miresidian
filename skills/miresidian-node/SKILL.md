# Miresidian Node 项目开发

围绕真实业务完成 Node 项目，以业务契约、资源生命周期和实际验证为主线。先按任务范围选择流程，沿用适用的结构、契约和依赖：

| 任务 | 执行重点 |
| --- | --- |
| 新建或整体构建业务 | 介绍并确认 features，优先用官方工具初始化新项目，在项目内生成方案，确认后实现业务；已有项目复用骨架 |
| 维护已有项目 | 定位本次行为及版本影响；次版本及以上先写方案，补丁级修复和小范围维护直接实施相关修改与验证 |
| 按既有配置编译、打包或复现问题 | 核对实际版本与配置，执行相关检查和交付；复用有效选择，不因此新增方案、重选 features 或初始化 |

本 skill 中“整体构建”仅指业务整体设计与实现或重构，不包含例行全量编译、清理后重建、CI 重建或重新打包。任务确需改变 feature 组合或业务契约时，再进入相应的选择、版本评估及方案流程。

本 skill 提供开发流程、关键决策和完成条件。框架与工具的具体 API、命令、兼容性及规范从对应版本的官方资料取得；skill 不声明固定适配版本，不要求项目跟随 skill 或最新发行升级。

## 1. 确认需求与实际版本

读取目标项目的 AGENTS.md、README、调用说明及相关源码；新项目先确认业务操作、协议依据、配置、对象身份、目标平台和交付范围。业务与资源资料不完整时先查证，影响正确性的缺口再询问，不猜测设备协议。

先识别目标 Node 自身版本、实际依赖的框架版本、解析到的组件及启用能力，依据 Cargo.toml、Cargo.lock 和 Cargo 解析结果；工具独立核对已安装版本，不从框架版本推算工具、ABI 或协议版本。新项目先确认所选版本已发布，再用 Cargo 生成真实锁文件。

维护已有 Node 时，以该节点当前源码、调用说明及对应发布记录确定业务契约，保留适用依赖，不套用新模板或其他节点的行为。同一仓库、工作区或任务包含多个节点、框架版本时，分别按目标包及其实际解析结果核对依赖、能力和资料，不以仓库根版本或另一个节点代表全部项目。跨节点/DLL 协作须另核对 ABI、通信和资源共享协议兼容性，不因同属 Miresidian 就假定互通。

以下入口用于发现官方资料，进入后选择实际使用的精确版本：

| 资料 | 官方入口与用途 |
| --- | --- |
| 框架发行 | [crates.io](https://crates.io/crates/miresidian)：确认可用版本、包说明和仓库信息 |
| Rust API | [docs.rs](https://docs.rs/miresidian)：切换到依赖版本后查 API、类型与 feature；首页可能跳转 latest |
| 开发手册、专题与示例 | [官方仓库](https://github.com/MyMires/miresidian)：在对应发布标签或已核实的发布提交中，从文档中心查节点开发、能力、ABI 和示例 |
| 工具 | [CLI](https://crates.io/crates/miresidian_cli)、[Pack](https://crates.io/crates/miresidian_pack)、[Windows TestFlow](https://crates.io/crates/miresidian_testflow_windows)：按各自实际版本查包说明、发布源码及工具文档 |

- 设计时查所需能力与约束，实现前确认相关 API、声明和调用布局，初始化或交付前查工具用法；只读取本次涉及的资料，复用已确认且仍有效的结果。
- 在线文档必须核对版本与来源；不将搜索摘要、master/latest 或其他版本的示例直接作为当前契约。仓库标签与 crate 版本分别核对，工具文档不能仅按根框架标签选择。
- API、宏、参数解析、元数据及 ABI 等技术契约按实际依赖版本查证；开发流程、注释和声明风格等规范按用户要求及项目规则确定适用范围。采用现行规范前核对旧版本是否支持，以及是否改变已有调用契约；涉及参数描述、预填、默认或输出的变化须纳入本次范围并评估兼容性，不因查到新规范顺带迁移旧节点。
- 文档缺失时查对应发布包中的 README、示例、Rustdoc 和源码；可通过发布包的源码修订信息定位仓库提交，不猜标签。具体命令在执行前再核对实际程序的版本与帮助。
- 已有完整且版本匹配的资料可直接复用；无法联网时使用同版本本地资料。明确关键资料缺口及其影响，在无法确认的能力上暂停依赖该结论的实现，继续其他有依据的工作，不擅自升级或用本地框架替代已发布依赖。
- 记录本次实际采用的资料版本与入口，便于复核；不为此额外建立常驻版本表、文档副本或报告文件。官方技术资料用于确认契约，项目范围与执行约束遵循用户要求及项目规则。

### 构建前展示 features 并由用户选择

新建或整体构建 Node、调整 feature 组合前，按目标项目及其实际依赖版本，向用户展示支持的 features 与功能配置清单。依据项目 Cargo.toml、Cargo.lock、解析结果及对应版本官方资料，覆盖 Node 自身声明的 features，以及实际框架/直接依赖向该 Node 提供的可选能力；区分项目开关与依赖开关，不把依赖全部传递特性都当作用户选项。新项目从拟采用的已发布版本及模板资料只读查证，不为列清单先初始化项目，也不照搬最新版本的能力表。

用便于比较的表格列出各项：feature 名称与所属包/版本、功能与适用场景、默认是否启用、当前项目实际是否启用、启用/关闭方式、关联配置及默认值，以及依赖、互斥或组合约束和平台/交付影响。编译开关与节点声明、运行时 Config/Input 分别说明；不能仅启用 feature 就声称业务已接入。配置细节仅覆盖该能力实际需要的内容，未查证的支持范围或默认值明确标为待核实。

给出符合业务需求的推荐组合和理由，明确请用户选择保留、启用或关闭哪些项，以及仍需决定的配置。新项目先完成选择再初始化，初始化后再生成业务方案；未选择时保持待确认，不把默认项、推荐或沉默当作同意，不执行依赖该选择的模板初始化、依赖修改或构建。已有明确选择/授权覆盖当前版本、目标与组合时记录依据并复用；局部维护保留已确认组合，不要求每次小修复重选。项目没有可选 feature 时说明事实及固定能力，不虚构选项。

把所选组合、是否保留默认 features、关联配置及验收范围落实到项目依赖、节点实现、构建/打包参数和调用说明；需要方案时同时写入方案，小改动不为记录选择另建计划。验证实际启用结果与选择一致；不能只在临时检查命令中打开。多个 Node 或不同依赖版本分别列清单和记录选择，交付时报告实际组合及验证边界。

## 2. 初始化项目并按范围管理方案

新建或整体构建 Node 时，先完成上节的 features 介绍、推荐和用户选择。新项目核对对应版本的官方工具文档及实际程序帮助，优先用支持所选框架版本的工具初始化骨架；已有项目复用现有目录与骨架，不重新初始化或覆盖已有源码。新项目初始化时不要求已有方案文件，也不在项目外建立临时规划文件；初始化只落实已选择的模板与功能配置，不提前编写业务代码。随后根据用户意见，在目标 Node 的 plans/YYYY-MM-DD-主题.md 生成业务实现方案，沿用项目既有方案目录。

工具无法覆盖所选版本时，先核对具体限制。项目规则允许且任务授权涵盖初始化时，可依据同版本官方模板或示例手工建立最小骨架，仍使用已发布精确依赖和 Cargo 生成的真实锁文件，并单独验证结构、编译与调用；后续方案及确认顺序不变。缺少可靠依据或项目规则要求工具生成时，报告该项阻塞并继续有依据的其他工作，不擅自升级框架或工具。

已有 Node 先评估自身版本影响：次版本（MINOR）及以上更新必须在实现前建立或更新方案；补丁级修复、小范围维护、纯规范小改动无需强制写计划，直接实施并完成相关验证。不得为省略方案低估版本影响。用户明确要求方案时遵从其要求；调整 features 仍需用户选择，不因选择本身强制创建计划。

先按目标 Node 及其自身目标主/次版本（X.Y）查找已有方案；同一目标次版本更新共用一份方案，跨任务新增需求也先修订该文件的设计、步骤和验收，不因日期、主题或执行状态变化另建计划。原方案已部分或全部执行时，仍在原文件追加修订，保留原有决策、实施与验收事实，并更新新增事项的状态。尚无对应方案时才新建并明确所属 Node 与目标版本，进入新的主/次版本时另建；不同 Node 或框架版本不能代替目标 Node 自身的版本归属。补丁级小修小改仍不强制建立方案，已有所属版本方案时可补充相关修订和验证结果。需要方案时，写清目标/非目标、实际版本与依据、所选 features 与配置、具体实现方式和职责、Config/Input/Output、资源所有权/共享状态/生命周期、失败与并发边界、影响文件、版本/文档/交付影响、步骤及验收证据。详见[方案文件与实施约束](references/planning.md)。

向用户说明方案路径、设计要点与执行条件。新建或整体构建 Node 在业务实现前取得方案确认，骨架初始化不受该门禁限制；已有确认/授权涵盖当前具体方案时记录依据并继续。用户要求先审方案时必须等待，不以一般性任务授权或沉默代替确认。方案不自动授权发布、部署等外部操作。

有方案时严格按其设计、接口、资源边界和步骤实施；调整前先修订并说明原因和影响，满足必要确认条件后继续。除上述骨架初始化外，需要方案的实现不得先执行再补计划或反写记录掩盖偏离。

## 3. 实现契约与业务

有方案时，开始每一步前核对其设计、目标文件、前置条件和验收项；无需方案的小改动直接按已明确的需求实施。明确操作、参数来源与顺序、选项、单位、缺失/空值、输出和错误条件，核对对应版本的生命周期入口及框架生成职责。按需要选择多实例、多通道、配置协调、物理资源共享、批量调用或格式转换，并落实实际依赖配置、节点声明或通信层接入；避免预先开启全部能力。

参数声明及预填要求按前述版本与规范适用规则查节点开发手册的“参数声明规范”，按[契约检查](references/review.md#契约与输入输出)验收。区分宿主预填、运行时默认与项目业务约定；skill 不另行维护技术规则。

区分业务对象身份、配置兼容性与物理资源所有权。共享独占连接时明确资源身份、通信提供者、完整请求—响应事务、关闭引用和故障边界，不能用兼容租约登记成功证明连接已共享。

独立节点只依赖 crates.io 已发布的框架精确版本，锁文件由 Cargo 生成；禁止框架 path/git 依赖及 patch/replace/paths 等本地覆盖。框架尚未发布时明确依赖阻塞；框架或工具升级必须属于任务范围。

新项目沿用前述初始化的骨架，已有项目保留适用结构。契约模块集中声明节点和平台方法并委托业务；业务、校验、协议与资源管理归所属模块。优先复用框架、标准库和适用依赖，按真实职责拆分，具体审查见 [开发与交付检查](references/review.md)。

先完成“验证配置 → 建立资源 → 执行业务 → 返回结果 → 关闭资源”的调用链，再补齐其他操作和失败清理。实现真实协议、超时及生命周期；业务模块、类型、字段和方法尽量用详细中文 Rustdoc 维护，内容按官方开发规范的“注释与文档”执行，同步调用说明与业务烟测；模板回显与模拟能力明确标识。

## 4. 验证本次行为

按本次需求、所选能力和 [开发与交付检查](references/review.md) 选择相关检查，完成项目门禁和所选能力的验收；有方案时对应其验收矩阵。预期行为以本次查证的版本契约及业务要求为依据。

复用仍有效的验证结果，修复后先重跑失败项与直接受影响项。耗时检查先说明目的和预计耗时，超出预估时重新评估范围。无目标资源时验证协议样本、模拟响应和资源状态，明确真实通信未验证；取得本次平台、位数和能力所需证据后结束。

## 5. 完成交付

按项目规则同步自身版本、真实锁文件、带日期的 CHANGELOG 和调用说明。DLL 交付提供目标产物、对应头文件、版本/架构/SHA-256 清单及可执行示例，并取得目标平台的实际加载调用证据。

按实际 Pack 版本核对业务文档生成能力。支持时由工具链将业务方法的文档注释自动并入节点 Markdown，无需 AI 重复整理；核对源码、项目说明和交付副本一致，保留手写部署/ABI 内容。不支持时，项目规则允许即可依据源码及实际版本契约手工维护本次受影响说明，核对交付副本并报告采用的方式；项目强制要求自动生成时，仅将该验收项列为阻塞。替代方式仍须满足约定的文档内容与验证，不声称已自动生成，不为此擅自升级依赖或工具。

交付目录及依赖加载要求查对应版本的开发规范与工具说明，并按[交付检查](references/review.md#验证与交付)验收。

有方案时，交付前在文件中逐项记录实施状态、验收证据及偏离的修订依据，并报告路径；无需方案的小改动不补写计划。报告已实现业务、Node 与框架/工具版本、产物位置、实际验证和剩余事项，分别说明模拟、DLL 调用与真实资源结果。提交、标签和发布依用户授权及项目规则执行；框架、节点、工具和 skill 各按实际变化维护，不相互触发无关升级。
