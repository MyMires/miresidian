# Node 项目规范

本规范约束 Node 项目的源码结构、依赖方向、测试组织与完成条件。新建节点或修改生产代码、测试时，必须在实现前读取并按本次范围执行。用户明确要求优先，目标项目的适用规则同时遵守；局部维护不扩大为全项目重构。节点宏、参数、生命周期及 ABI 契约另见 [节点设计与实现约束](node-contract.md)。

## 实现前明确职责

在已有方案、任务说明或必要的模块注释中说明本次涉及模块的职责、依赖方向、资源/状态归属，以及相应测试的位置与验证目标。简单修改用几句话即可，不强制新建架构文档或目录清单。新建或构建项目仍遵守主 skill 的方案确认门禁。

新增模块必须能说清独立职责、由谁调用以及持有什么状态；已有模块能够自然承载时优先复用。拆分已有代码时，先确定需要隔离的变化，再移动实现。仅减少行数、搬移测试或增加转发层，不视为职责拆分完成。

## 项目目录结构

新建 Node 项目以以下布局为基线；已有项目保留等价且职责清晰的命名，不为符合示例批量重命名。标为“按需”的项目只有在有真实实现或验收用途时才创建，禁止空文件占位。

```text
<node-project>/
├── Cargo.toml                 # 独立 crate、已发布框架的精确依赖和所需 features
├── Cargo.lock                 # Cargo 实际解析生成，纳入版本管理
├── AGENTS.md                  # 本项目模块边界、测试约定及有效检查命令
├── README.md                  # 项目用途、开发入口和调用说明位置
├── CHANGELOG.md               # 项目自身版本及带日期修订
├── src/
│   ├── lib.rs                 # 入口、模块声明和必要导出
│   ├── node.rs                # 完整节点契约及简短适配
│   ├── device.rs              # 实际业务对象；文件名可按领域概念调整
│   ├── protocol.rs            # 按需：独立协议编解码与响应校验
│   └── transport.rs           # 按需：独立连接与底层 I/O
├── tests/                     # 按需：仅通过公开接口运行的集成测试
│   └── contract.rs            # 平台描述、参数映射与调用契约的测试示例
├── docs/
│   └── <节点显示名>.md        # 真实契约、ABI、参数、错误和调用示例
└── tools/                     # 按需：本节点实际使用的烟测及辅助脚本
    └── smoke.testflow         # 按交付需要维护真实配置与操作
```

- 真实业务实现必须有独立于 node.rs 的归属。device.rs 是设备节点的示例名称；服务、计算或其他资源节点按实际业务对象命名，也可直接复用已有业务模块。模板回显不要求创建空业务对象，但不能当成业务完成。
- 基础依赖方向是 node → 业务对象；业务对象按需使用协议、传输或独立计算模块。协议编解码不反向依赖节点，底层传输不解释业务；不要把同一业务流程拆成节点和业务对象各维护一半。
- 已有明确协议名称时可使用 scpi.rs 等具体名称替代 protocol.rs，不同时建立只有转发关系的同义模块。只存在少量紧密相关的协议/I/O 时可先归入业务模块，node.rs 仍保持契约入口职责。
- 只有真实会话管理职责才增加 session.rs；多种传输实现确有共享边界时可使用 transport.rs + transport/tcp.rs、transport/serial.rs。不预建 manager、utils、common 等无具体职责的模块。
- 业务模块的单元测试默认留在对应文件的测试模块内；私有测试明显影响阅读时再使用 device/tests.rs 等外置子模块。node.rs 不保留测试模块声明，不把所有生产文件统一扩展成只有 tests.rs 的目录。具体判断见 [测试组织与有效性](#测试组织与有效性)。
- tests/ 只使用项目实际提供的公开接口；无法通过公开接口验证的私有行为改用所属模块的单元测试，不为生成 contract.rs 增加公开 API。共享集成测试夹具可按真实使用范围放在 tests/support/，由用例显式引用。
- target/ 与 dist/ 是生成目录，不属于源码模块。源码提交中排除 target/；dist/ 是否归档或上传按项目交付要求决定，不能把旧产物当作本次验证结果。

## 模块职责与依赖

以下是职责边界，不是必须生成的文件列表；按实际概念命名，简单节点允许合并紧密相关的实现。

| 职责 | 应承担的内容 | 边界 |
| --- | --- | --- |
| crate 入口 | 模块声明和必要导出 | lib.rs 不承载业务、协议或测试夹具实现 |
| 节点契约入口 | 节点声明、业务对象持有字段、操作及 Config/Input/Output 标注、简短调用适配 | node.rs 优先保证契约可浏览，设备状态、检查和业务流程交由业务对象实现 |
| 业务或协议 | 设备/业务状态、状态与参数有效性检查、业务流程、命令编码、响应解析与校验 | 依据真实职责组织，可独立验证的规则不依赖具体节点的宏契约和平台调度 |
| 传输 | 连接、字节读写及底层资源释放 | 不反向依赖具体节点或负责解释业务输出 |
| 会话（确有需要时） | 连接持有、完整请求—响应事务、节流或会话状态 | 有实际资源与状态职责才提取，不为每个节点固定生成 session.rs |

- 生产模块不得依赖测试实现或夹具；模块不得形成循环依赖。节点可组合业务、协议和传输能力，下层实现不得反向调用具体节点契约；需要协作时使用明确的参数、结果或小型接口。
- 保持所有权、关闭责任和事务互斥边界清晰；不能因拆文件缩小锁范围、拆断请求—响应事务或改变失败清理行为。
- 默认私有，仅在真实调用边界需要时扩大可见性；不得为方便集成测试公开生产内部实现。
- 使用概念.rs；存在多个协作的生产子职责时再使用概念.rs + 概念/，父文件收敛模块声明及必要导出。测试子模块可按需要单独存在，但不算生产职责已拆分。不使用 mod.rs，不机械生成 node.rs + operations.rs；契约入口委托业务对象是正常边界，不得在两者之间再建立只有转发函数的多余层次。
- 文件达到约 300–500 行时审查实现与测试各自的职责和阅读负担，不设统一硬上限。独立职责混杂时即使文件很短也应拆分；单一职责的长文件可保留，并在必要注释或审查说明中解释边界。不得仅为满足行数建立目录或逐文件汇报行数。

## node.rs 契约可读性

node.rs 是集中展示宏标记契约的唯一源码入口；已有项目使用等价文件名时，该文件适用同一边界。节点结构体与标注方法保留在同一文件，清楚展示节点名称、初始化 Config、各操作 Input/Output、默认值与单位；不要把契约拆散到多个业务文件或用额外自定义宏隐藏标注。

本节是必须遵守的文件边界，不是“建议尽量简短”。node.rs 只允许宏标记的节点结构体与契约方法，以及承载它们必需的 use、impl、结构体持有字段和契约注释；方法体仅做对外部业务对象的简短委托及必要直接映射。不放其他未标记的手写函数/方法、辅助类型、常量定义、测试实现或测试模块声明。不得在该文件实现被操作调用的业务子逻辑，即使该逻辑很短或只有一个调用方也必须归入对应业务模块。

| 内容 | node.rs 中的要求 | 实现归属 |
| --- | --- | --- |
| 宏标记的节点结构体及操作方法、Config/Input/Output、签名与契约注释 | 必须集中展示；仅附带必需的 use、impl 和对象持有字段 | node.rs |
| 构造节点包装、委托业务方法、直接映射契约参数/结果及错误上下文 | 允许保留必要的简短适配 | node.rs |
| ensure_open、validate_config、measure_inner、execute_command 等业务辅助方法或函数 | 禁止定义在 node.rs，不以名称作为唯一判断标准 | 业务对象或实际负责模块 |
| 协议解析、请求拼装、范围校验、状态机、重试、节流、读写及多步骤业务流程 | 禁止作为操作方法体或其子逻辑留在 node.rs | 业务、协议、会话或传输模块 |
| 业务辅助类型、协议常量、模拟夹具及大段测试实现 | 禁止为实现操作方便而放入 node.rs | 实际负责模块或测试模块 |

- 不得通过私有函数、额外 impl、内嵌模块、嵌套函数、闭包或本地宏把业务子逻辑留在契约文件；把操作方法缩成调用本文件辅助方法不算完成拆分。重命名契约文件也不能绕过本节。
- “契约适配”仅指平台契约与已有业务 API 之间的直接映射，不包括设备状态判断、参数业务有效性校验或业务计算。适配本身已形成复杂算法或独立流程时，也应提取到有明确职责的适配模块；不允许用“适配”统称全部实现。
- 新增操作先确定业务 API 及实现归属，再编写薄契约入口；已有操作修改时检查其本次涉及的调用链，不把新增子逻辑继续放回 node.rs。业务对象必须能够在不依赖具体节点契约类型的情况下执行和测试相关业务。

- 节点结构体通常只持有设备或业务对象及契约适配确需的字段。连接、关闭状态、缓存和业务配置由业务对象持有，不在节点中重复维护一份状态。
- 操作方法保留完整宏标注和签名，方法体仅做简短的调用委托、契约参数/结果映射和必要错误上下文适配。设备可用性检查、业务参数有效性检查、重试、节流、协议处理及多步骤业务流程放入业务对象，不因方法体较短而重复散落在各操作中。
- 初始化和关闭仍由节点声明为框架生命周期操作；实际连接建立、初始化失败清理、关闭与 Drop 兜底由持有资源的业务对象实现。节点只完成对象包装与契约返回值映射，不复制框架生命周期检查。
- 业务对象按真实概念命名和组织，优先复用已有实现，不强制增加 device.rs 或通用驱动层。不要求方法体严格一行，但每个保留步骤必须能解释其契约适配用途；纯业务步骤应下沉。
- node.rs 不放测试实现、模拟夹具或测试模块声明。契约测试通过已有公开接口在 tests/ 验证；业务内部行为在业务模块测试，不为测试扩大节点可见性。普通业务模块仍可内联单元测试。

验收时必须枚举 node.rs 中所有手写项，确认仅有宏标记的节点结构体/契约方法及必要承载语法，并审查方法体是否仅做委托或直接映射；再沿本次操作调用链检查业务实现实际位于哪个文件。发现业务辅助函数或被隐藏的业务实现必须移出后才能通过，不以“private”“仅调用一次”“代码很短”为豁免理由。读者必须能直接辨认对外操作、参数来源与顺序、默认值、单位及输出；不能仅凭文件较短或新增业务文件判定合格。

## 有限选项与业务类型

有限离散取值的 Config/Input 必须执行 [完整选项与内部枚举规则](node-contract.md#有限取值必须声明完整选项)。对外由 node.rs 的宏标注展示全部合法选项；对内优先用业务模块中的枚举承载选择，类型定义、解析及有效性检查不进入契约文件。新建或修改相关参数时，先核实真实支持集合，再同步外部契约、内部映射、默认值与测试；不能只把自由文本改成单一默认文本。

## 测试组织与有效性

- 测试按被验证职责归属：协议样本与解析归协议，读写与分帧归实际负责模块，设备状态、检查与资源生命周期归业务对象，节点契约及其调用映射归契约测试。分帧等职责由实际设计决定，不在节点末尾集中全部测试。
- 单元测试默认与所属模块就近组织，允许使用内联的 `#[cfg(test)] mod tests`；node.rs 按上一节保持契约可读性。测试或夹具明显妨碍阅读实现、需要单独维护时才外置；不因测试成组就强制建立目录，也不要求每个生产模块都创建只有 tests.rs 的目录。
- 外置私有单元测试可使用所属模块的测试子模块，例如 device.rs 声明 `#[cfg(test)] mod tests;`、用例放在 device/tests.rs；通过 `super` 访问私有项。该布局是可选方式，不能用目录数量判断质量。
- 仅通过公开接口验证平台契约或完整调用链的集成测试放在 crate 根目录 tests/；依赖私有细节的调用链测试保留在相关内部测试模块。测试位置不能迫使生产 API 扩张。
- 模拟传输、脚本响应和记录器按使用范围组织：单模块使用则留在该模块测试内，确有多个使用者时再提取共享夹具。夹具仅在测试构建中启用，不建立无实际复用者的通用模拟框架。
- 每组测试须能说明它保护的可观察行为和失败条件。按本次改动覆盖正常、相关边界和错误路径，断言业务输出、错误类别、资源释放或实际副作用；不能只检查任意报错、文件存在、私有代码形状或重复实现逻辑。
- 缺陷修复须有能复现原问题的回归用例；在可用基线或隔离环境中确认修复前失败、修复后通过。环境无法复现时说明限制，不声称已取得该证据，不回退或覆盖用户工作区来演示失败。
- 结构重组后保留原有有效断言并运行迁移及直接受影响测试；不得通过删除用例、忽略测试或削弱断言让检查通过。确需改变旧预期时，说明对应的契约变更或旧断言错误。
- 无硬件测试应可重复运行，真实资源测试明确环境前提；模拟通过不能代替真实通信验收。更多证据选择见 [节点验证与验收](verification.md)。

## 交付前执行与审查

对本次变更逐项给出结论和简短依据，可复用已有方案、代码与测试结果，不强制新增报告文件：

| 检查项 | 应有的依据 |
| --- | --- |
| 项目布局 | 基础文件职责齐全；可选模块、测试目录及脚本有真实用途，无空占位或重复转发层 |
| 契约可读性 | 枚举 node.rs 所有手写项，确认仅有宏标记的节点结构体/契约方法及必要承载语法，无辅助实现和测试声明；本次操作的业务子逻辑实际位于其他职责模块 |
| 职责归属 | 新增/变更模块负责什么；协议变化、传输替换是否需要改动无关业务 |
| 依赖与资源 | 调用方向清晰，无循环或生产依赖测试；连接所有权、事务及关闭责任清楚 |
| 拆分收益 | 形成可独立理解或验证的边界；没有为缩短文件引入空转发层或固定目录模板 |
| 选项完整性 | 有限取值参数的宏选项覆盖全部实际支持值，默认值属于集合；内部枚举/解析与外部选项对应，集合外值明确失败 |
| 测试质量 | 测试归属明确，断言对应行为；相关正常/失败路径及回归用例有实际结果 |
| 检查执行 | 执行项目要求且适用于本次改动的结构、格式、静态检查与测试，记录失败和未验证项 |

发现本次相关违规必须修复，受外部条件阻塞时明确报告未完成；不能以“已按规范拆文件”或“测试全绿”替代上述审查。局部改动发现的无关历史问题可单独记录，不扩大修复范围。

新建项目时将实际采用的模块边界、测试约定和有效检查命令写入项目 AGENTS.md；已有项目仅在本次改变约定时补充，保留原有内容。不复制整份 skill，不臆造尚不存在的检查命令。需要创建或打包时查阅 [工具操作参考](commands.md)。

已有提交钩子或 CI 门禁必须通过，不得跳过。新增自动门禁须有明确检查对象且属于用户任务范围，不能把每个 Node 任务扩成工具开发。当前文档规定 AI 的执行与审查责任，本身不安装自动检查器；工具结构检查、编译及测试仅证明其覆盖范围，不能自动证明职责划分合理。
