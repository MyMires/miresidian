# 维护历史与协作复盘

[文档中心](../README.md) · [现行开发规范](../coding-standards.md) · [版本管理](../versioning.md)

本页归档从现行手册移出的历史原文，保留当时的背景、版本、验证与待解决事项，不代表当前发行状态或新增维护门禁。实际发行记录见各组件 CHANGELOG，现行规则按上方入口查阅。

## 10. 工具链与 skill 协作复盘（2026-11-01）

本节复盘统一工具入口、Cargo 安装、Node skill 和框架发布这次会话。记录执行方的具体错误及其原因，用于约束后续判断；不是把用户的纠正归因为“需求不清”，也不是把已解决的问题继续列作当前故障。

### 10.1 主要根因：没有稳定维护目标、边界与完成条件

用户的目标一直有清晰主线：保留独立工具，提供统一入口和 Cargo 安装方式；让 AI 能完成后续 Node 项目；合理验证后发布实际更新的组件。我没有把这条主线持续作为决策依据，而是让最近处理的问题决定下一步工作。

这导致三种反复出现的失误：把尚未核实的方案直接实现；用新增工具、文档或检查的数量代替交付效果；遇到纠正时只反转上一项动作，没有重新判断用户真正要求的边界。后续多次解释和承诺，也没有及时转化为正确执行。

本次责任在执行方。用户要求控制时间与 AI 用量，不等于接受缺失验证；指出设计问题，不等于要求反复停下来重新批准已经授权的工作。

### 10.2 把“统一使用”与“合并项目”混为一谈

**踩坑表现：** 对统一入口的理解偏离“原工具继续独立，增加统一调用”。用户需要反复强调工具项目、调用入口和未来扩展的关系，早期计划也没有给出足够具体的统一指令与原指令对照。

**为什么踩坑：** 我优先考虑实现组织形式，没有先明确哪些边界必须保持。把“统一”当作代码或项目层面的整合，没有区分用户入口、进程调用、安装管理与项目依赖，方案因此缺少可核对的行为。

**后续要求：** 先确定必须保留的独立性，再描述统一入口调用什么、参数如何转换、由谁安装/升级、失败怎样返回。设计评审使用实际命令对照和可执行的典型流程；不能只写“整合工具链”。当前实现与对照见 [CLI 说明](../../tools/miresidian-cli/README.md)。

### 10.3 未先核实 Cargo 的边界，就设计安装体验

**踩坑表现：** 曾引入 Python 用户安装器，随后又围绕项目内工具目录设计处理；项目尚不存在时，new 还需要临时安装 Pack。Cargo 不支持的自定义 cargo install 参数，也是在方案讨论后才核实。

**为什么踩坑：** 我从“怎样把程序下载或复制到目录”出发，没有从 Rust 项目的包管理、安装记录、升级/降级和 PATH 语义出发。把后续特殊处理当作局部需求去补，没有识别 new 需要临时引导安装暴露的是安装边界本身不合适。同时，先承诺指令形状、后检查底层命令能否实现，造成返工。

**后续要求：** 影响整体方案的底层限制应优先用帮助或最小调用核实。Rust 配套工具默认沿用 Cargo 安装与版本管理；不同于生态默认的安装依赖或目录布局，须有实际需求依据。不要无依据增加第二套包管理。

本次最终采用 cargo install miresidian_cli 安装入口，再由 cargo miresidian install --full 安装独立后端；--full 属于 CLI 子命令，不能扩展原生 cargo install。工具位于 Cargo 安装根目录，同根替换当前版本；不是默认多版本并存。完整系统构建环境自动配置仍是单独待办，不能把“工具已安装”写成“环境已配齐”。

### 10.4 接受局部建议时缺少整体推演，需求也未完整落地

**踩坑表现：** 在全局/项目内安装等讨论中，局部方案不断修补；用户要求的两个框架版本别名、命令层级、构建与打包职责、平台与位数等事项，需要逐项再次纠正和补充。

**为什么踩坑：** 我把“及时回应用户”误当成接受每个局部方案，没有检查它与已确定边界是否冲突，也没有把已接受要求保留为实现约束。沟通完成被错误地当成需求已进入代码、帮助和文档。

**后续要求：** 对影响流程的选择，用首次安装、新建项目、已有项目、升级/降级和失败恢复等相关场景做简短推演。用一份简要的已接受要求记录核对最终实现、帮助与示例，保留别名等精确要求。发现设计矛盾时指出原因并给出可执行修正，不以持续增加特例掩盖矛盾；简单任务不额外建立庞大管理文档。

### 10.5 Skill 偏成工具手册，遗漏 Node 开发的关键决策

**踩坑表现：** 第一版 skill 大量描述工具怎么调用，Node 需求设计、业务实现与验收成为次要内容。重写后，对 features 仍只提概念，没有完整说明如何选择、配置、声明和验证。初期也只安装了本地副本，未同时纳入框架仓库维护。

**为什么踩坑：** 我沿用了刚完成工具链工作的材料和思路，按手头信息写作，没有从下一位 AI 需要完成的 Node 任务反推内容。把“包含工具用法”当成“能指导完成项目”，又把格式/引用校验通过误当成内容覆盖充分。遗漏 features 并非无资料可查，而是没有逐项检查框架能力是否落实到项目配置和行为。

**后续要求：** 主文档围绕需求、Config/Input/Output 契约、项目结构、业务/通信、生命周期、验证和交付组织；工具用法放子文档。能力说明至少回答“何时需要、依赖如何配置、节点如何声明、运行时改变什么、如何取得验证证据”。例如 instances/lease 必须同时说明 Cargo features 与节点标注，不只列名称或盲开全部能力。

内容评审应能沿一个实际 Node 需求找到实现与验收依据，不以文档篇幅或校验器通过作为充分条件。完整 skill 已保存在 [skills/miresidian-node](../../skills/miresidian-node/SKILL.md)，两份副本按 AGENTS 中的规则同步，包含引用、元数据和新增文件。

### 10.6 验证范围失控：把“更多检查”当作“更可靠交付”

**踩坑表现：** 局部工具/文档修改被扩展到全工作区、多平台和宿主环境问题；已有通过结果没有充分复用，构建、检查、状态读取和日志输出存在重复。用户反馈大量时间和 AI 用量消耗在验证上。

**为什么踩坑：** 我没有先明确每个检查要回答的问题、已有证据何时失效，以及什么条件满足后应停止。面对不确定性时倾向增加检查，用“更全面”缓解不确定，却没有评估它是否改变本次交付结论。原有全量检查清单也被机械套用，没有按实际修改选择范围。

检查发现新的环境问题后，我又把它们直接纳入当前任务，导致验证成为新的工作来源。缺少阶段性的必要性判断，使一次已经足够的验证继续消耗时间。频繁轮询和读取整段日志进一步增加了 AI 用量。

**后续要求：** 执行前明确本次改动、交付目标、最小所需证据和可复用结果；每项新增检查必须对应未被回答的问题。修复后优先重跑失败项和直接受影响项。耗时超出预估时重新判断必要性；不因出现无关失败就自动扩大任务。满足停止条件后结束，具体范围规则见本规范第 7 节。

例如，纯 skill/规范修改检查内容与引用；dlltool 参数修复验证相关 Windows 调用和目标构建；只有实际影响共享运行时或多个组件时，才扩大到对应回归。两种位数都受影响时检查两种位数，不据此推导出必须重跑所有框架和工具测试。

### 10.7 从“验证过多”摆到“取消必要验证”

**踩坑表现：** 用户批评扩大验证后，我取消了整条 CI。取消发生在 MinGW 安装阶段，修复后的参数和 Windows 构建尚未执行，随后只能报告“已修改，但未验证通过”，又让用户再次推动执行。

**为什么踩坑：** 我把纠正理解为对上一动作的否定，按情绪变化选择相反动作，没有保持“质量证据必须具备、成本必须受控”这两个同时成立的目标。为了迅速表现出收缩范围，取消了与故障直接相关的必要检查。

**后续要求：** 先区分必要检查与无关检查，只停止后者；不能把没有证据的修改当作修复完成。若现有 CI 一个作业串联了相关和无关步骤，应选择相关作业、以目标步骤结果记录证据，并停止后续无关工作。只有任务不再需要某项验证时才取消它，不以省时为由跳过直接受影响的行为。

本次最终只重跑 Windows 作业；x64/x86 构建、DLL 加载/卸载步骤成功后，停止后续工具测试，再发布框架。工作流因后续步骤被取消而显示 cancelled，不应据此否认已成功的目标步骤，也不能反过来宣称整条 CI 全绿。

### 10.8 Windows 配置修复只验证“看起来合法”，未验证参数实际传递

**踩坑表现：** Windows CI 先后暴露 MSYS2 路径假设、PATH 中工具位数选择，以及 dlltool 路径双引号问题。最后一种把引号保留为文件名内容，rustc 调用的路径形如 '"D:/.../dlltool.exe"'，因此返回 Windows 文件名语法错误。参数修复见提交 8b51d7f。

**为什么踩坑：** 我用本地熟悉的路径和命令解析经验推断远端环境，没有始终采用环境实际输出。参数经过 YAML、PowerShell、环境文件、Cargo、rustc 和 Windows 进程创建，不是单层 shell 命令；给环境变量值增加引号，并不保证下游把它当成转义语法。我确认了选项存在和配置格式，却没有取得这条完整调用链成功的证据。

同样，滚动 stable 的 lint 差异、Windows 默认日志编码等，说明验证环境与既有结果的对应关系必须明确。某条库测试通过或某个版本支持参数，不足以证明宿主工具组合配置正确。

**后续要求：** 使用 action/环境提供的真实路径；明确链接器和 dlltool 的目标位数。排查时查看下游实际收到的参数，区分语法引号和字面字符。对跨进程参数修复，以相关目标实际构建为证据，不以静态字符串检查替代。不要为修复一个已知路径问题重建整个环境方案。

### 10.9 技术状态解释不完整，让用户承担判断与推动责任

**踩坑表现：** 发布状态、框架验证、工具套件验证和 Windows CI 失败被混在较长汇报中；“Windows CI 仍未修复”没有及时讲清失败阶段、原因和实际影响。指出执行错误后，有时停在解释和承诺，没有完成仍在授权范围内的必要工作。

**为什么踩坑：** 我按执行顺序描述过程，没有围绕用户需要作出的判断报告结论。虽然没有把失败写成通过，但只列状态没有说明其意义，也没有承担直接相关问题的闭环责任。诚实披露是必要条件，不能代替完成任务。

**后续要求：** 先给出当前交付结论，再说明阻塞的具体步骤、受影响对象和下一步。在已授权范围内继续完成必要动作；用户询问状态本身不自动授权新的设计、改动或发布。说明 CI 配置失败时，不暗示已经确认运行时/DLL 故障；说明部分步骤通过时，不夸大为全量验证完成。

### 10.10 发布判断要区分组件、版本和证据的不同作用

**踩坑表现：** 会话中需要反复确认 CLI 从独立版本起步、同一 Cargo 安装根目录的版本替换行为，以及框架发布是否会重复上传所有子项目。旧组件标签与当前清单存在管理方式上的差异，也不能直接据此推断有未发布功能。

**为什么踩坑：** 我没有始终把“统一入口/发行”“独立 crate 版本”“依赖可用性”“源码标签”和“registry 上传”分别看待。若只看本地版本或标签差异就发布，会把管理性变更误当成功能更新，或无差别重发整个工作区。

**后续要求：** 发布前形成实际候选列表：各组件本地版本、真实已发布版本、实质变更与待发布依赖。只发布本次需要且尚未发布的组件；依赖版本已可用则直接复用，不联动升版。无需补发开发中间版本，不为统一发布要求所有组件同号。Cargo 包验证、registry 发布成功和 Git 源码可访问分别核对，不重复执行等价 dry-run 与正式发布验证。

本次工具发布为 CLI 0.2.1、Pack/TestFlow 各 0.12.0；之后框架发布只上传根 crate 0.16.5、0.16.6，未重复发布已有子库与工具。这些是本次事实，不是以后应固定采用的版本号。

### 10.11 错用版本标签检查，静态路径假设又制造额外排查

**踩坑表现：** 在纯规范提交之后，曾对各独立组件直接执行要求标签指向当前 HEAD 的检查，得到失败；但组件标签本应停留在各自版本提交。发布后还假设归档必然保留在固定 target/package 路径，读取不存在的文件，产生额外工具调用。

**为什么踩坑：** 我把检查命令的适用条件当成通用条件，没有先确认它检查的是“版本提交”还是“当前工作树”。对临时构建产物也用预期路径代替实际可用状态。这些验证自身的错误被误当成需要继续排查的产品问题，进一步拉长了任务。

**后续要求：** 版本提交后执行规定的标签核对；之后只有纯规范变更时，不移动旧标签，检查该提交适用的版本门禁，并核对原标签快照和组件内容。不能为让检查通过而改写标签，也不能把当前 HEAD 不等于旧版本提交写成产品失败。

读取归档前先确定实际产物是否仍存在；只有发布确认确实需要时，才读取 Cargo 实际产物或 registry 真实发布包。已取得足够发布证据后，不再追加文件检查来制造新的完成条件。

### 10.12 后续执行时的最小决策检查

开始相关工作及收到用户纠正后，重新核对以下问题；简单任务用简短说明即可，不把本复盘变成新的繁重审批或全量检查流程：

1. **目标是什么？** 当前是在完成 Node 业务、维护 skill、修改工具还是发布组件？最近的提问是否只是要求解释状态？
2. **哪些边界必须保持？** 已确认的项目独立性、Cargo 管理方式、版本别名、交付平台和用户授权是什么？
3. **什么证据足够？** 每项检查回答什么问题，哪些既有结果仍有效，哪些失败直接阻断交付？
4. **何时停止？** 必要证据齐备后立即交付；缺什么就处理什么，不默认增加更多组件、平台、依赖或环境工作。
5. **交付是否真的成立？** 真实业务、相关能力配置、必要验证、版本/产物和实际发布状态是否各有依据？不把解释、计划、模板或工具运行成功当作项目完成。

这次最应改变的是判断方式：保留用户的完整目标，主动指出设计矛盾，按因果关系选择验证，在足够证据上完成交付。不能只记住“少跑测试”或“多写文档”，否则仍会在过度执行与交付不足之间反复。

## 独立工具与统一套件

CLI 和套件首版为 0.1.0，pack 与 TestFlow 独立候选为 0.12.0；不使用框架版本。统一入口只启动后端进程，不建立工具库依赖。toolset.toml 固定各工具实际版本，套件构建核对 Cargo.toml 和程序 --version；公开发布另行授权。新增 workspace 成员及 CI 交付配置使根包补丁升到 0.16.1，其他框架 crate 保持原版本。

CLI/套件在历史 0.2.1 阶段确立以下安装方式。用户通过 cargo install miresidian_cli 安装入口，再用 install --full 安装后端；全部由 Cargo 管理用户级目录和安装记录，update/use 替换同一根目录中的当前版本，不默认多版本并存。移除用户安装脚本；新增管理与批次发行功能属于 CLI 独立次版本，CI/交付配置调整使根包补丁升到 0.16.6，后端保持 0.12.0。公开发布仅针对用户授权的三个工具 crate，先后端后 CLI。

Node skill 托管于框架仓库，按开发流程、资料查询方式和验收依据的实际变化维护，不设置固定框架/工具适配版本。框架或工具升版不要求同步修订或重新安装 skill，skill 修订也不要求已有 Node 升级。纯 skill 规范变化不提升产品版本，记入带日期的规范修订并在提交说明记录版本影响；涉及可构建、可调用或可交付行为时，按实际受影响组件另行判断。skill 暂不设置独立版本号或发布流程。

## 架构验证与模块加载记录

当前 C ABI 为 v8，新增完整请求入口并保留 v7 的两个调用入口；异步任务及显式跨实例批次现阶段通过 Rust API 使用。新增外部异步入口需独立评审并提升 ABI。

0.15.1 为根运行时增加可释放的承载模块加载引用：启动业务池及生命周期池之前获取引用；回收全部工作线程后才释放引用。Windows 使用 FROM_ADDRESS 获取引用，不使用不可逆 PIN；Unix 用 dladdr 和 RTLD_NOLOAD 持有既有映射，不使用 NODELETE。主程序静态链接场景不增加动态库引用。

宿主在任何入口调用期间仍须持有自己的加载引用。宿主释放自身引用时，框架引用保护存活工作线程；Rust 嵌入调用方排空任务、关闭实例并调用 shutdown_executor 后，框架额外引用可以释放。关闭同时检查两池的在途工作及外部执行器引用，任意池仍忙时两池都保持原状；线程回收期间阻止重建。

C ABI v7 的现有同步接口保持参数、返回方式和文本内存契约。它不提供最终执行器关闭操作，因此 C 宿主释放句柄不保证立即卸载，空闲执行器可能将模块保持至进程退出。其他加载引用、线程局部析构以及租约服务的既有 Windows PIN 仍可延后实际卸载。外部异步任务接口属于可选扩展，本次没有加入。

加载器边界依据 [Windows GetModuleHandleExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandleexw)、[FreeLibrary](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibrary) 和 [dlopen/dlclose](https://man7.org/linux/man-pages/man3/dlopen.3.html)；通过 libc 复用平台声明，不自行定义 Unix ABI。测试夹具 module_lifetime 的私有 probe 导出只用于原生加载器测试，不属于节点公共 C ABI。

本轮 Linux Debug DLL 验证使用两个各等待 30ms 的模拟请求，5 次采样中位数：同步同实例 61.78ms、不同实例 30.96ms；async 同实例 64.08ms、不同实例 32.40ms。该观测仅说明示例的执行重叠，实际目标资源性能需另测。

0.16.0 广播语义以[实例规范](../instances.md#broadcast-的执行源与输出规则0160)为准：固定调用通道1一次并复制完整输出，其他通道无需同值；跳过目标保持空槽位，源通道被跳过时整批跳过，不选择后续源。此次同步与 Future 调度同时修正，并以实际业务计数等于1验收。
