本文档定义 Miresidian 项目的默认编码、测试与文档维护规范。除非后续有明确的架构决策覆盖，本项目中的实现、评审和重构均应遵守这些规则。

## 0. P0：版本管理是提交前置条件

版本影响、依赖与锁文件、修订归档、提交门禁、发布和不可移动标签统一按[版本管理规范](versioning.md)执行；本页不重复维护版本命令或当前版本表。

## 0.1 按更新范围管理方案，并严格按方案实现

本节同时约束框架、运行时与子 crate、宏、开发工具和独立 Node 项目。先按实际变化评估版本影响：次版本（MINOR）及以上更新必须在实现前形成方案；补丁级修复、小范围维护和纯规范小改动无需强制写计划，直接实施并完成相关版本、文档与验证要求。不得为省略方案将应升次版本的公开 API 或兼容性变更降为补丁。用户明确要求方案时按用户要求执行。

Node 新建的 features 介绍与选择、工具初始化及业务方案顺序，统一按 [Node skill 主流程](../skills/miresidian-node/SKILL.md#2-初始化项目并按范围管理方案)执行；已有项目保留现有骨架。下文的方案先行要求以该初始化顺序为例外。

### 方案适用与执行顺序

1. 检查项目规则、现有代码与文档、实际版本和必要官方资料，明确需求、范围及版本影响；小改动不为流程另建计划文件。
2. 对需要方案的已有项目，在项目根目录的 plans/YYYY-MM-DD-主题.md 建立方案，沿用项目既有目录约定。同任务已有尚未执行的方案时，只更新原文件，不因日期变化或用户追加意见另建一份；已执行方案保留实际记录，后续调整不得抹去已有事实。
3. 新 Node 按上述 skill 流程初始化后，将业务方案直接保存在该项目内；不在项目外建立临时规划文件。
4. 向用户说明方案路径、设计要点及执行条件。新建或整体构建 Node 在业务实现前取得方案确认，骨架初始化不受该确认门禁限制；已有明确授权覆盖当前具体方案时记录依据并继续。用户要求先审阅/确认方案时必须等待，不能以沉默或一般性任务授权替代。
5. 对需要方案的任务，除上述 Node 骨架初始化外，方案落盘前只做只读调研及方案编写。实现开始前写清关键决策、分步修改及验收标准，不在编码时猜测影响正确性的设计；范围调整先修订方案并满足必要确认条件。发布、推送和部署仍须有对应授权。

### 方案文件必须能指导实现

| 内容 | 必须说明的事实 |
| --- | --- |
| 目标与范围 | 用户需求、期望行为、非目标、保留边界、假设、待确认问题及执行/确认依据 |
| 现状与版本 | 相关实现和文档、实际组件/依赖版本、官方资料依据、当前缺口及影响；不能混用源码候选与已发布能力 |
| 实现设计 | 职责/模块边界、具体实现方式、关键类型/接口、完整调用链、资源所有权/共享状态/引用计数、正常和失败生命周期、并发/超时/取消；不适用项明确标注 |
| 对外契约 | 参数/输出、默认与错误、行为变化、兼容性、ABI/协议、迁移与交付；不能只写“接入租约”等能力名称 |
| 变更与版本 | 待改文件/组件、依赖变化、各组件版本影响、同步文档及 CHANGELOG 范围；纯规范明确说明不升版理由 |
| 实施与验收 | 有先后关系的步骤，每步对应文件和设计项；需求对应的验证方法、通过标准、证据位置、验证边界及完成条件 |

需要方案的任务按实际复杂度组织内容，目标、具体改法、文件范围、版本影响和验收不能缺失；无需方案的小改动不受本表约束。图示用于说明复杂关系，不强制每个任务增加图或额外报告。

### 实现方式严格遵循方案文件

以下要求适用于需要方案的任务；小改动无需为满足本节补写计划。

- 将当前有效方案作为实现和评审依据。每步开始前核对对应设计、目标文件、职责边界、前置条件与验收项；代码结构、接口、默认/错误、资源共享粒度、生命周期及验证范围必须与文件一致。只有任务清单或聊天中的口头承诺，不能代替具体方案。
- 不得在实施时擅自替换实现方式、改变架构或扩大范围，也不得用“已有 API”“测试通过”代替计划要求的真实端到端效果。依赖方案的后续步骤必须等前置设计和实现成立后再执行。
- 发现方案不可行或需要调整时，先停止受影响步骤，修改方案，记录原决策、调整原因、影响文件/行为/版本/验收和执行依据，再继续。目标、架构、公开契约、资源所有权/共享状态/生命周期、兼容性或验收标准变化时，先完成用户要求的必要确认；不相关且已授权的步骤可继续。
- 严禁先实现后补方案、反向改写方案掩盖偏离、删除原验收标准来迁就代码，或把未确认事项标为已确认。保留方案修订与决策依据；实施中记录实际状态、阻塞及必要证据，不伪造事前记录。
- 完成前按“需求 → 方案设计 → 实施步骤/代码 → 验证证据”逐项核对，在方案中记录完成、未完成及实际验证边界。未实现、未验证或仍受阻的条目不能标为完成，交付说明必须如实披露。

此处是执行和评审要求。现有版本门禁只能检查其既有版本规则，不自动证明方案先后顺序或实现语义一致，不能以检查通过替代方案审查。

## 1. 源码与模块结构

- 源码按单一职责合理拆分，避免将多个独立领域、协议或职责堆积在同一个文件中。
- 一个文件承担一个清晰的职责；当文件约超过 300 至 500 行，或已经包含多个独立职责时，应评估拆分。
- 使用 Rust 新式模块结构，禁止使用 `mod.rs`。

  ```text
  src/
  ├─ transport.rs
  └─ transport/
     ├─ tcp.rs
     └─ serial.rs
  ```

  父模块文件负责声明子模块和公共导出，具体实现位于同名目录中。
- 所有 crate 一律遵循下列层级判断，禁止按文件数量或个人偏好临时改变：

  1. `lib.rs` 只承担 crate 入口、模块声明和必要公开导出，不承载业务、协议或代码生成实现。
  2. 一个概念只有一个实现文件时使用 `概念.rs`；不能为了“看起来整齐”额外建立目录。
  3. 一个概念确有两个及以上协作子职责时，使用 `概念.rs + 概念/`。父文件只声明子模块、收敛内部公共项并说明该概念边界；子文件按职责命名，禁止使用 `概念_xxx.rs` 代替目录。
  4. 相互构成一个完整语义单元的状态与对外方法应保留在同一模块；不得机械拆成 `node.rs` 与 `operations.rs`。验证私有实现细节的单元测试可紧邻实现；仅通过公开接口验证平台契约或跨 crate 行为的测试应放入 crate 根目录的 `tests/`。
  5. 超过 300 行不是自动建目录的理由。先按职责拆分；若仍是单一职责，可保留单文件并以注释说明边界。

  该规则对运行时框架、属性宏 crate 和各独立 Node 项目完全相同。
- 涉及运行时、属性宏或实例节点边界的变更，必须先确认职责归属与三个层次的影响范围；不得为
  了快速实现而把框架生成逻辑写入实例节点，或让具体通信依赖反向进入根运行时 crate。
- 属性宏是节点平台契约的唯一生成入口。实例节点只能通过结构体、方法、参数和方法输出标注
  声明契约；不得手写 `GetFunctions`、`GetInitConfig`、操作字符串分发、`Node` 实现或
  DLL 的 C ABI 导出。
- 主框架的运行时源码集中在根目录 `src/`。属性过程宏和可独立构建的设备模块因 Rust 的 crate 边界而各自拥有独立的 `src/`。

## 2. 命名与可见性

- 类型、trait 和枚举使用 `PascalCase`。
- 函数、模块、字段和局部变量使用 `snake_case`。
- 常量使用 `SCREAMING_SNAKE_CASE`。
- 默认保持私有；仅当跨 crate、宏生成代码或调用方确实需要时才暴露 `pub` API。
- Rust 内部采用惯用命名，例如 `invoke`、`init_device`、`close_device`。
- C ABI 导出符号、请求字段、平台确定方式和对外 Operation 名称，以项目实际版本的[平台调用契约](c-abi.md)及头文件为准；本规范不复制具体入口签名或 ABI 版本，禁止把旧版示例当成当前契约。
- 物理量、超时、长度等应通过名称或文档表明单位，例如 `timeout_ms`、`voltage_v`、`maximum_bytes`。
- 禁止散落的魔法数字；协议常量、默认值和状态码必须定义为具名常量或明确的枚举成员。

## 3. 错误处理与安全边界

- 普通调用错误必须通过项目统一错误类型和 `Result` 返回，不使用 `panic!` 作为业务错误处理方式。
- 禁止 Rust panic 穿过 C ABI 边界；FFI 入口必须捕获并转换所有异常路径。
- `unsafe` 必须最小化并隔离在 FFI 或确有必要的底层模块中。
- 每个 `unsafe` 块必须附带说明，阐明其前置条件和安全性理由；含有不安全调用约束的公共 API 应提供 `# Safety` 文档。
- 需要公开 ABI 结构时必须使用 `#[repr(C)]`，并仅使用布局稳定的字段类型；当前入口使用 C 字符串与 DLL 持有的 JSON 返回文本，不公开 Rust 结构体或字符串指针数组。
- 不允许将 Rust 的 `String`、`Vec<T>`、引用、trait 对象或未标注布局的 Rust 结构体直接暴露给 C、Python、LabVIEW 或其他外部调用方。

## 4. 跨语言契约

- 平台可见输入输出仅支持稳定、通用且可明确序列化的类型：数值、布尔值、UTF-8 文本、字节数组、基础类型一维数组、可选值、规范化枚举值和空返回值。
- C ABI 文本统一使用 UTF-8，并明确空指针、空数组、空字符串与错误值的含义。
- 由 Rust 分配并交给外部调用方读取的内存，其所有权、有效期与回收策略必须由 ABI 文档明确。当前 JSON 文本 ABI 在 DLL 当前线程中保存响应；返回指针只在同一线程下一次调用前有效，调用方应立即复制且不得释放。
- ABI 的函数名、参数顺序、调用约定、所有权和版本必须记录在公开头文件与 ABI 文档中。任何破坏性修改必须新增 ABI 版本，而不是覆盖旧入口。
- 统一调用模型为 `Function + Config + Input -> Output`。`operation` 表示 Rust 内部节点调度语义；宿主调用符号及参数形式按实际版本的 C ABI 契约绑定，不从内部名称或旧签名推断。

## 5. 设备节点、并发与资源

参数声明按[节点开发手册](宏驱动开发.md#参数声明规范)执行；对象生命周期与配置身份分别见[实例管理](instances.md)和[Config 身份](config-identity.md)。

- 设备节点的生命周期必须明确：初始化成功后才可执行需要连接的操作；关闭后不可继续使用该实例。
- 不使用可变全局变量保存普通状态。共享资源必须通过明确的同步原语和所有权模型管理。
- 锁的持有范围应尽量小；通信事务需要原子性时，应覆盖完整的请求—响应过程，避免不同调用交错读取响应。
- 串口、TCP 会话、缓冲区和临时探测资源必须具有明确的释放责任，并在失败路径中同样释放。
- 共享同一物理串口的节点必须校验物理通信参数的一致性。

## 6. 注释与文档

- 公开发布前，为 README、CHANGELOG 和 Release Notes 提供中英文版本。
- 仓库自行编写的源码说明、模块注释及 Rustdoc 使用中文；保留 API/协议专名、标准 `# Safety` 标题和 `SAFETY:` 标记，英文发布资料另按双语交付约定维护。
- 注释长度按职责确定：简单转发可简短；宏生成、条件编译、取消、回滚、并发、ABI 和 unsafe 必须说明实际前提、执行顺序、所有权及失败边界。禁止仅翻译陈旧说明而不核对实现。

- 每次提交前，必须逐项检查本次变更涉及的源码注释、Rustdoc、公开头文件、框架文档、节点发布说明与测试说明；发现缺失、陈旧或语义不清的内容必须在同一提交中完善。
- 提交前审查不得只确认编译通过。凡是新增、删除或改变了对外行为、参数、返回值、内存约定、默认值、错误规则或调用顺序，都必须确认相应注释和文档与最终产物一致。
- 每次修改公共行为、参数规则、错误行为、ABI 或调用顺序时，必须同时更新对应文档与测试。
- 文档随组件版本同步与发布后核对，统一按[版本规范](versioning.md#指导性文档与版本同步门禁)执行。
- 每个发布 DLL 必须在发布目录根部附带与节点同名的说明文档。说明至少包含：DLL 文件与适用位数、完整 C ABI 函数签名、每个参数与返回值的类型/语义/所有权/有效期、状态与错误规则、可复制的调用示例，以及已支持平台的逐项配置方式。
- Node 按主入口与依赖组织交付：每个节点对应架构目录的顶层只放一个供用户调用的 Node DLL；随附的第三方及辅助运行时 DLL 统一放入该架构目录下的 `dependencies/`，不作为本节点的对外调用入口。无此类依赖时无需创建空目录，也不要求新增 `references/`。节点说明必须明确主入口文件名、适用位数及依赖目录用途。
- 整理 DLL 到依赖子目录时，须确认实际加载方式并在目标 Windows 上验证加载和调用。目录命名不会让系统自动搜索该目录；应按项目实际情况处理依赖解析，不将此规范理解为现有打包工具已自动收集或配置第三方 DLL。

  ```text
  dist/设备节点/
  ├── 设备节点.md
  ├── CHANGELOG.md
  ├── manifest.json
  └── windows-x64/
      ├── device_node.dll
      ├── miresidian.h
      └── dependencies/
          ├── VendorSdk.dll
          └── Communication.dll
  ```

- DLL 文档必须将 ABI 返回值命名、JSON 字段与节点业务输出区分清楚；不得只列出节点操作清单而遗漏入口函数的配置和调用契约。
- 公共 Rust API 使用 Rustdoc 注释，至少说明用途、参数、返回值、错误条件以及线程或资源约束。
- 注释应解释设计原因、协议限制和不明显的边界条件，而非重复代码字面含义。
- C ABI 变更必须同步更新 `abi/api/miresidian.h`、`docs/c-abi.md` 与相关节点发布说明。
- 驱动接口、默认值、Operation 名称、配置标签、输入输出标签发生变化时，必须同步更新该驱动的调用说明。
- 属性宏的行为、固定入口映射、自动命名或生成代码的职责边界发生变化时，必须同步更新
  `docs/宏驱动开发.md`，并为该行为增加或更新回归测试。

## 7. 测试与验证

### 验证范围与交付边界

- 审核应先核对 skill、项目声明及文档契约中的使用约束，再结合实际使用场景与影响评定缺陷和严重程度；非法输入用例应验证约定的拒绝或错误行为。
- 开始验证前，按本次实际改动、受影响组件和交付目标确定范围；优先使用能证明相关行为的最小检查集合。验证必须回答具体问题，不得默认扩展为整个框架、所有工具或全部平台的验证。
- 规范/skill 文档修改检查内容、命令、引用和格式；工具修改检查受影响的命令、参数与真实进程行为；节点业务修改检查相关编译、业务契约与生命周期；ABI、宏、共享运行时、依赖或构建配置修改，应覆盖实际受影响的组件、特性和目标平台。范围较大时执行下节对应的完整检查。
- 执行耗时或高用量验证前，简要说明检查目标、范围及预计耗时；优先运行能尽早发现问题的检查。仅因验证耗时较长不需要新增确认流程；额外授权仍按用户指令和操作本身判断。
- 验证超出预估时重新判断剩余检查是否必要，并及时报告原因和剩余工作；不盲目等待、反复轮询或累积重复检查。优先读取检查摘要和失败上下文，避免重复输出全量日志增加 AI 用量。
- 在源码、依赖、构建配置、工具版本和目标环境未发生相关变化时，复用已通过的结果，不重复执行等价检查。修复后先重跑失败项与直接受影响项；只有新的改动、失败证据或尚未覆盖的交付要求才扩大范围。
- 不把节点交付扩大为框架回归，不把工具发布扩大为完整宿主环境修复；无关问题记录待办。直接阻断本次交付的问题应明确说明并处理，不得以缩小验证范围掩盖失败。
- 针对用户要求交付的平台和位数验证；只有交付范围或共同契约确实涉及多个目标时，才扩展平台矩阵。明确区分结构检查、编译、打包、DLL 实际加载、无硬件调用和真实硬件验证，不能用前一项声称后一项通过。
- 达到交付所需的验证条件后结束验证，不为追求全绿继续增加无关检查。交付报告记录实际检查及结果、复用结果的适用范围、未验证项和已知失败；不得把未运行或失败的项目写为通过。
- 本规则用于选择有依据的验证范围，不免除版本门禁、受影响契约的必要检查或用户明确要求的检查。

### 行为覆盖要求

- 参数默认值、文本与数组编解码、Base64、数值格式和错误输入必须有单元测试。
- 生命周期应有集成测试，至少覆盖 `init -> invoke -> close`、重复关闭、初始化失败和未初始化调用。
- C ABI 必须有 FFI 测试，覆盖 UTF-8、JSON 字符串数组、返回 JSON 的状态/稳定代码/消息/业务结果、错误码和错误信息；跨平台 DLL 产物还应在目标平台实际加载调用验证。
- 修复缺陷时应新增能够复现该问题的回归测试。
- 有真实硬件的通信验证与无硬件的协议/模拟验证应分开；硬件测试不得成为基础契约测试的前提。

## 8. 格式化、静态检查与依赖

- 下列命令是 Rust 源码完整检查集合；按上节确定范围后使用，不是每次规范、skill、单个节点或工具修改都必须执行的默认清单。涉及框架公共行为或多个组件的变更，使用与影响范围对应的完整检查；局部变更可通过 `-p <crate>`、具体测试目标和所需特性限定范围，并在交付说明中记录选择依据：

  ```text
  cargo fmt --all -- --check
  cargo clippy --workspace --all-targets --locked -- -D warnings
  cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
  cargo test --workspace --all-targets --locked
  cargo test --workspace --all-targets --all-features --locked
  cargo build --workspace --release --locked
  ```

- DLL 发布前验证本次交付位数的产物、导出符号和 ABI 行为；同时交付 x64 与 x86 时须分别验证。
- 新增依赖前优先评估标准库和成熟维护的 crate，避免为通用能力重复造轮子；只有现有方案无法满足性能、安全、许可证或跨平台约束时，才实现自有基础设施。
- 选择第三方 crate 时，至少评估维护活跃度、文档与测试质量、目标平台支持、版本兼容性、许可证和已知安全风险；在变更说明或模块文档中记录其用途与关键取舍。
- 直接依赖必须声明经验证的版本范围，并由 `Cargo.lock` 锁定实际构建版本；升级依赖时审查破坏性变更，重新执行依赖影响范围内的完整检查。共享依赖影响多个组件时覆盖所有受影响组件，不默认扩展到无关项目。
- 第三方库应封装在合适边界内，不得让供应商 SDK 或具体通信实现泄漏为 Miresidian 的稳定公共 API。

## 9. Git 提交消息

提交消息使用 Conventional Commits 格式，首行必须为：

```text
<类型>: <中文摘要>
```

允许的类型为：`feat`、`fix`、`refactor`、`docs`、`test`、`build`、`chore`。摘要使用中文，简洁描述本次提交的主要结果，不使用句号。

```text
feat: 优化串口数据通信与编解码接口
refactor: 统一框架结果与错误命名
docs: 固定平台参数描述透传规则
```

提交前必须执行 `git diff --check`，确认不包含构建产物、凭据或无关改动；提交信息必须符合本节格式。

## 构建环境

本仓库仅包含 Miresidian 框架及其 ABI、编解码、过程宏和打包工具。

### 最低工具链

最低 Rust 版本为 **1.89**。框架使用 Rust 2024、let chains，以及 Rust 1.89 稳定的跨平台文件锁 API。
CI 在 Linux 和 Windows 上使用 1.89 执行全工作区、全目标、全特性编译，并运行异常恢复与多进程租约回归。

```bash
cargo +1.89.0 check --workspace --all-targets --all-features --locked
```

框架开发先按[测试与验证](#7-测试与验证)确定范围，完整检查命令见[格式化、静态检查与依赖](#8-格式化静态检查与依赖)。

### 节点项目

节点应作为独立 Cargo 项目维护，且只能从 crates.io 依赖已发布框架的精确版本；禁止 path/git 和本地覆盖。框架尚未发布时先完成发布，不得伪造锁文件或以本地构建替代 registry 验证。Windows DLL 的交叉编译、`cargo miresidian-pack` 和烟测工具均由节点项目自行配置与维护。

### Windows GNU 目标的手动配置

以下说明针对 Pack 支持的 Windows GNU x64/x86 目标。工具安装与系统构建环境是两个步骤；按项目实际依赖确认 Rust MSRV，不因已安装 CLI 就假定 target、链接器或原生库齐备。

先检查 `rustc --version`、`cargo --version`、`rustup target list --installed`，再按本次交付位数安装目标标准库：

```text
rustup target add x86_64-pc-windows-gnu
rustup target add i686-pc-windows-gnu
```

仅交付一种位数时只安装对应项。rustup 不提供系统交叉链接器；Windows 宿主可用 MSYS2 的 MinGW-w64 GCC/binutils，MSVC 工具链不能替代 GNU 目标。按 [MSYS2 环境说明](https://www.msys2.org/docs/environments/) 安装并在其终端执行：

```text
pacman -S --needed mingw-w64-x86_64-gcc mingw-w64-i686-gcc
```

确认实际安装根目录，所选 mingw64/bin 或 mingw32/bin 中的 gcc.exe、dlltool.exe 都存在并可执行，将需要的 bin 加入 PATH。下面是节点项目 `.cargo/config.toml` 示例；`C:/msys64` 必须替换为本机实际位置，保留项目原有配置，只加入本次所需目标：

```toml
[target.x86_64-pc-windows-gnu]
linker = "C:/msys64/mingw64/bin/gcc.exe"
rustflags = ["-C", "dlltool=C:/msys64/mingw64/bin/dlltool.exe"]

[target.i686-pc-windows-gnu]
linker = "C:/msys64/mingw32/bin/gcc.exe"
rustflags = ["-C", "dlltool=C:/msys64/mingw32/bin/dlltool.exe"]
```

Linux 宿主使用发行版提供的 MinGW-w64 GCC 与 binutils；确认 `x86_64-w64-mingw32-gcc`、`x86_64-w64-mingw32-dlltool` 或对应的 `i686-w64-mingw32-*` 可执行。沿用同样目标表，将 linker 改为实际交叉 gcc 路径，dlltool 改为同位数工具路径。其他宿主也须提供所选 GNU 目标工具链，不将未验证环境视为已支持。

也可以使用 Cargo 的 `CARGO_TARGET_<大写目标>_LINKER` 与相应 RUSTFLAGS 环境变量。环境变量中的 dlltool 路径不得额外包入字面双引号；TOML 示例的引号是配置语法。环境变量、项目配置与构建启动目录的优先级按 [Cargo 配置说明](https://doc.rust-lang.org/cargo/reference/config.html) 核对，工作区构建从工作区根读取配置。

用项目真实 registry 依赖先执行相应目标的 `cargo check --locked --target ...`，再用 `cargo miresidian build --arch x64` 或 x86 构建；pack 已包含构建，不必先重复 build。缺目标标准库时补 target，找不到 gcc/dlltool 时检查所选路径与位数，其他 native library 错误按业务依赖要求处理。最后在匹配位数的 Windows 宿主加载 DLL 并执行烟测；Linux 交叉编译不能证明 Windows 加载成功。`install --full` 不自动完成这些系统配置。
