本文档定义 Miresidian 项目的默认编码、测试与文档维护规范。除非后续有明确的架构决策覆盖，本项目中的实现、评审和重构均应遵守这些规则。

## 0. P0：版本管理是提交前置条件

[版本管理规范](versioning.md) 是本仓库最高优先级的工程门禁，用户指令优先。每次相关源码、公开契约、依赖、MSRV、构建或工具更新，必须先评估并提升版本，在同一提交中同步依赖/锁文件、归档修订记录及当前示例，验证后创建并核对标签。只写 Unreleased 或只完成代码提交均不满足要求；不得等待用户再次提醒。

首次检出启用 `git config core.hooksPath .githooks`。提交前运行 `python3 tools/check_versions.py --base HEAD`，钩子校验暂存区；提交后运行 `python3 tools/check_versions.py --require-tag` 核对版本提交。禁止跳过检查或移动既有标签。纯测试/规范文档更新按版本规范记录“版本影响：无”及理由。

## 1. 源码与模块结构

- 源码按单一职责合理拆分，避免将多个独立领域、协议或职责堆积在同一个文件中。
- 一个文件承担一个清晰的职责；当文件约超过 300 至 500 行，或已经包含多个独立职责时，应评估拆分。
- 使用 Rust 新式模块结构，禁止使用 `mod.rs`。

  ```text
  src/
  ├─ transport.rs
  └─ transport/
     ├─ tcp.rs
     └─ serial.rs
  ```

  父模块文件负责声明子模块和公共导出，具体实现位于同名目录中。
- 所有 crate 一律遵循下列层级判断，禁止按文件数量或个人偏好临时改变：

  1. `lib.rs` 只承担 crate 入口、模块声明和必要公开导出，不承载业务、协议或代码生成实现。
  2. 一个概念只有一个实现文件时使用 `概念.rs`；不能为了“看起来整齐”额外建立目录。
  3. 一个概念确有两个及以上协作子职责时，使用 `概念.rs + 概念/`。父文件只声明子模块、收敛内部公共项并说明该概念边界；子文件按职责命名，禁止使用 `概念_xxx.rs` 代替目录。
  4. 相互构成一个完整语义单元的状态与对外方法应保留在同一模块；不得机械拆成 `node.rs` 与 `operations.rs`。验证私有实现细节的单元测试可紧邻实现；仅通过公开接口验证平台契约或跨 crate 行为的测试应放入 crate 根目录的 `tests/`。
  5. 超过 300 行不是自动建目录的理由。先按职责拆分；若仍是单一职责，可保留单文件并以注释说明边界。

  该规则对运行时框架、属性宏 crate 和每个 `constellation` 实例节点完全相同。
- 涉及运行时、属性宏或实例节点边界的变更，必须先确认职责归属与三个层次的影响范围；不得为
  了快速实现而把框架生成逻辑写入实例节点，或让具体通信依赖反向进入根运行时 crate。
- 属性宏是节点平台契约的唯一生成入口。实例节点只能通过结构体、方法、参数和方法输出标注
  声明契约；不得手写 `GetFunctions`、`GetInitConfig`、操作字符串分发、`DeviceNode` 实现或
  DLL 的 C ABI 导出。
- 主框架的运行时源码集中在根目录 `src/`。属性过程宏和可独立构建的设备模块因 Rust 的 crate 边界而各自拥有独立的 `src/`。

## 2. 命名与可见性

- 类型、trait 和枚举使用 `PascalCase`。
- 函数、模块、字段和局部变量使用 `snake_case`。
- 常量使用 `SCREAMING_SNAKE_CASE`。
- 默认保持私有；仅当跨 crate、宏生成代码或调用方确实需要时才暴露 `pub` API。
- Rust 内部采用惯用命名，例如 `invoke`、`init_device`、`close_device`。
- C ABI 导出符号和对外 Operation 名称以契约为准。当前稳定调用入口为 `miresidian_invoke` 与 `miresidian_invoke_with`。
- 物理量、超时、长度等应通过名称或文档表明单位，例如 `timeout_ms`、`voltage_v`、`maximum_bytes`。
- 禁止散落的魔法数字；协议常量、默认值和状态码必须定义为具名常量或明确的枚举成员。

## 3. 错误处理与安全边界

- 普通调用错误必须通过项目统一错误类型和 `Result` 返回，不使用 `panic!` 作为业务错误处理方式。
- 禁止 Rust panic 穿过 C ABI 边界；FFI 入口必须捕获并转换所有异常路径。
- `unsafe` 必须最小化并隔离在 FFI 或确有必要的底层模块中。
- 每个 `unsafe` 块必须附带说明，阐明其前置条件和安全性理由；含有不安全调用约束的公共 API 应提供 `# Safety` 文档。
- 需要公开 ABI 结构时必须使用 `#[repr(C)]`，并仅使用布局稳定的字段类型；当前入口使用 C 字符串与 DLL 持有的 JSON 返回文本，不公开 Rust 结构体或字符串指针数组。
- 不允许将 Rust 的 `String`、`Vec<T>`、引用、trait 对象或未标注布局的 Rust 结构体直接暴露给 C、Python、LabVIEW 或其他外部调用方。

## 4. 跨语言契约

- 平台可见输入输出仅支持稳定、通用且可明确序列化的类型：数值、布尔值、UTF-8 文本、字节数组、基础类型一维数组、可选值、规范化枚举值和空返回值。
- C ABI 文本统一使用 UTF-8，并明确空指针、空数组、空字符串与错误值的含义。
- 由 Rust 分配并交给外部调用方读取的内存，其所有权、有效期与回收策略必须由 ABI 文档明确。当前 JSON 文本 ABI 在 DLL 当前线程中保存响应；返回指针只在同一线程下一次调用前有效，调用方应立即复制且不得释放。
- ABI 的函数名、参数顺序、调用约定、所有权和版本必须记录在公开头文件与 ABI 文档中。任何破坏性修改必须新增 ABI 版本，而不是覆盖旧入口。
- 当前统一调用模型为 `Function + Config + Input -> Output`。`operation` 是 Rust 内部节点调度语义，`miresidian_invoke` 与 `miresidian_invoke_with` 是稳定 C ABI 导出名称。

## 5. 设备节点、并发与资源

- 设备节点的生命周期必须明确：初始化成功后才可执行需要连接的操作；关闭后不可继续使用该实例。
- 不使用可变全局变量保存普通状态。共享资源必须通过明确的同步原语和所有权模型管理。
- 锁的持有范围应尽量小；通信事务需要原子性时，应覆盖完整的请求—响应过程，避免不同调用交错读取响应。
- 串口、TCP 会话、缓冲区和临时探测资源必须具有明确的释放责任，并在失败路径中同样释放。
- 共享同一物理串口的节点必须校验物理通信参数的一致性。
- 新节点项目必须将业务对象主键声明为第一个初始化 Config 参数（`Config[0]`），例如端口名或设备地址。多实例 Config 关联只以该字段识别对象；空主键初始化必须跳过，不能用默认值、其他业务配置或框架字段替代。完整规则见 [实例管理](instances.md)。

## 6. 注释与文档

- 每次提交前，必须逐项检查本次变更涉及的源码注释、Rustdoc、公开头文件、框架文档、节点发布说明与测试说明；发现缺失、陈旧或语义不清的内容必须在同一提交中完善。
- 提交前审查不得只确认编译通过。凡是新增、删除或改变了对外行为、参数、返回值、内存约定、默认值、错误规则或调用顺序，都必须确认相应注释和文档与最终产物一致。
- 每次修改公共行为、参数规则、错误行为、ABI 或调用顺序时，必须同时更新对应文档与测试。
- 每个发布 DLL 必须在发布目录根部附带与节点同名的说明文档。说明至少包含：DLL 文件与适用位数、完整 C ABI 函数签名、每个参数与返回值的类型/语义/所有权/有效期、状态与错误规则、可复制的调用示例，以及已支持平台的逐项配置方式。
- DLL 文档必须将 ABI 返回值命名、JSON 字段与节点业务输出区分清楚；不得只列出节点操作清单而遗漏入口函数的配置和调用契约。
- 公共 Rust API 使用 Rustdoc 注释，至少说明用途、参数、返回值、错误条件以及线程或资源约束。
- 注释应解释设计原因、协议限制和不明显的边界条件，而非重复代码字面含义。
- C ABI 变更必须同步更新 `abi/api/miresidian.h`、`docs/c-abi.md` 与相关节点发布说明。
- 驱动接口、默认值、Operation 名称、配置标签、输入输出标签发生变化时，必须同步更新该驱动的调用说明。
- 属性宏的行为、固定入口映射、自动命名或生成代码的职责边界发生变化时，必须同步更新
  `docs/宏驱动开发.md`，并为该行为增加或更新回归测试。

## 7. 测试与验证

### 验证范围与交付边界

- 开始验证前，按本次实际改动、受影响组件和交付目标确定范围；优先使用能证明相关行为的最小检查集合。验证必须回答具体问题，不得默认扩展为整个框架、所有工具或全部平台的验证。
- 规范/skill 文档修改检查内容、命令、引用和格式；工具修改检查受影响的命令、参数与真实进程行为；节点业务修改检查相关编译、业务契约与生命周期；ABI、宏、共享运行时、依赖或构建配置修改，应覆盖实际受影响的组件、特性和目标平台。范围较大时执行下节对应的完整检查。
- 执行耗时或高用量验证前，简要说明检查目标、范围及预计耗时；优先运行能尽早发现问题的检查。仅因验证耗时较长不需要新增确认流程；额外授权仍按用户指令和操作本身判断。
- 验证超出预估时重新判断剩余检查是否必要，并及时报告原因和剩余工作；不盲目等待、反复轮询或累积重复检查。优先读取检查摘要和失败上下文，避免重复输出全量日志增加 AI 用量。
- 在源码、依赖、构建配置、工具版本和目标环境未发生相关变化时，复用已通过的结果，不重复执行等价检查。修复后先重跑失败项与直接受影响项；只有新的改动、失败证据或尚未覆盖的交付要求才扩大范围。
- 不把节点交付扩大为框架回归，不把工具发布扩大为完整宿主环境修复；无关问题记录待办。直接阻断本次交付的问题应明确说明并处理，不得以缩小验证范围掩盖失败。
- 针对用户要求交付的平台和位数验证；只有交付范围或共同契约确实涉及多个目标时，才扩展平台矩阵。明确区分结构检查、编译、打包、DLL 实际加载、无硬件调用和真实硬件验证，不能用前一项声称后一项通过。
- 达到交付所需的验证条件后结束验证，不为追求全绿继续增加无关检查。交付报告记录实际检查及结果、复用结果的适用范围、未验证项和已知失败；不得把未运行或失败的项目写为通过。
- 本规则用于选择有依据的验证范围，不免除版本门禁、受影响契约的必要检查或用户明确要求的检查。

### 行为覆盖要求

- 参数默认值、文本与数组编解码、Base64、数值格式和错误输入必须有单元测试。
- 生命周期应有集成测试，至少覆盖 `init -> invoke -> close`、重复关闭、初始化失败和未初始化调用。
- C ABI 必须有 FFI 测试，覆盖 UTF-8、JSON 字符串数组、返回 JSON 的状态/稳定代码/消息/业务结果、错误码和错误信息；跨平台 DLL 产物还应在目标平台实际加载调用验证。
- 修复缺陷时应新增能够复现该问题的回归测试。
- 有真实硬件的通信验证与无硬件的协议/模拟验证应分开；硬件测试不得成为基础契约测试的前提。

## 8. 格式化、静态检查与依赖

- 下列命令是 Rust 源码完整检查集合；按上节确定范围后使用，不是每次规范、skill、单个节点或工具修改都必须执行的默认清单。涉及框架公共行为或多个组件的变更，使用与影响范围对应的完整检查；局部变更可通过 `-p <crate>`、具体测试目标和所需特性限定范围，并在交付说明中记录选择依据：

  ```text
  cargo fmt --all -- --check
  cargo clippy --workspace --all-targets --locked -- -D warnings
  cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
  cargo test --workspace --all-targets --locked
  cargo test --workspace --all-targets --all-features --locked
  cargo build --workspace --release --locked
  ```

- DLL 发布前验证本次交付位数的产物、导出符号和 ABI 行为；同时交付 x64 与 x86 时须分别验证。
- 新增依赖前优先评估标准库和成熟维护的 crate，避免为通用能力重复造轮子；只有现有方案无法满足性能、安全、许可证或跨平台约束时，才实现自有基础设施。
- 选择第三方 crate 时，至少评估维护活跃度、文档与测试质量、目标平台支持、版本兼容性、许可证和已知安全风险；在变更说明或模块文档中记录其用途与关键取舍。
- 直接依赖必须声明经验证的版本范围，并由 `Cargo.lock` 锁定实际构建版本；升级依赖时审查破坏性变更，重新执行依赖影响范围内的完整检查。共享依赖影响多个组件时覆盖所有受影响组件，不默认扩展到无关项目。
- 第三方库应封装在合适边界内，不得让供应商 SDK 或具体通信实现泄漏为 Miresidian 的稳定公共 API。

## 9. Git 提交消息

提交消息使用 Conventional Commits 格式，首行必须为：

```text
<类型>: <中文摘要>
```

允许的类型为：`feat`、`fix`、`refactor`、`docs`、`test`、`build`、`chore`。摘要使用中文，简洁描述本次提交的主要结果，不使用句号。

```text
feat: 优化串口数据通信与编解码接口
refactor: 统一框架结果与错误命名
docs: 固定平台参数描述透传规则
```

提交前必须执行 `git diff --check`，确认不包含构建产物、凭据或无关改动；提交信息必须符合本节格式。

## 构建环境

本仓库仅包含 Miresidian 框架及其 ABI、编解码、过程宏和打包工具。

### 最低工具链

最低 Rust 版本为 **1.89**。框架使用 Rust 2024、let chains，以及 Rust 1.89 稳定的跨平台文件锁 API。
CI 在 Linux 和 Windows 上使用 1.89 执行全工作区、全目标、全特性编译，并运行异常恢复与多进程租约回归。

```bash
cargo +1.89.0 check --workspace --all-targets --all-features --locked
```

框架开发先按[测试与验证](#7-测试与验证)确定范围，完整检查命令见[格式化、静态检查与依赖](#8-格式化静态检查与依赖)。

### 节点项目

节点应作为独立 Cargo 项目维护，且只能从 crates.io 依赖已发布框架的精确版本；禁止 path/git 和本地覆盖。框架尚未发布时先完成发布，不得伪造锁文件或以本地构建替代 registry 验证。Windows DLL 的交叉编译、`cargo miresidian-pack` 和烟测工具均由节点项目自行配置与维护。

## 10. 工具链与 skill 协作复盘（2026-11-01）

本节复盘统一工具入口、Cargo 安装、Node skill 和框架发布这次会话。记录执行方的具体错误及其原因，用于约束后续判断；不是把用户的纠正归因为“需求不清”，也不是把已解决的问题继续列作当前故障。

### 10.1 主要根因：没有稳定维护目标、边界与完成条件

用户的目标一直有清晰主线：保留独立工具，提供统一入口和 Cargo 安装方式；让 AI 能完成后续 Node 项目；合理验证后发布实际更新的组件。我没有把这条主线持续作为决策依据，而是让最近处理的问题决定下一步工作。

这导致三种反复出现的失误：把尚未核实的方案直接实现；用新增工具、文档或检查的数量代替交付效果；遇到纠正时只反转上一项动作，没有重新判断用户真正要求的边界。后续多次解释和承诺，也没有及时转化为正确执行。

本次责任在执行方。用户要求控制时间与 AI 用量，不等于接受缺失验证；指出设计问题，不等于要求反复停下来重新批准已经授权的工作。

### 10.2 把“统一使用”与“合并项目”混为一谈

**踩坑表现：** 对统一入口的理解偏离“原工具继续独立，增加统一调用”。用户需要反复强调工具项目、调用入口和未来扩展的关系，早期计划也没有给出足够具体的统一指令与原指令对照。

**为什么踩坑：** 我优先考虑实现组织形式，没有先明确哪些边界必须保持。把“统一”当作代码或项目层面的整合，没有区分用户入口、进程调用、安装管理与项目依赖，方案因此缺少可核对的行为。

**后续要求：** 先确定必须保留的独立性，再描述统一入口调用什么、参数如何转换、由谁安装/升级、失败怎样返回。设计评审使用实际命令对照和可执行的典型流程；不能只写“整合工具链”。当前实现与对照见 [CLI 说明](../tools/miresidian-cli/README.md)。

### 10.3 未先核实 Cargo 的边界，就设计安装体验

**踩坑表现：** 曾引入 Python 用户安装器，随后又围绕项目内工具目录设计处理；项目尚不存在时，new 还需要临时安装 Pack。Cargo 不支持的自定义 cargo install 参数，也是在方案讨论后才核实。

**为什么踩坑：** 我从“怎样把程序下载或复制到目录”出发，没有从 Rust 项目的包管理、安装记录、升级/降级和 PATH 语义出发。把后续特殊处理当作局部需求去补，没有识别 new 需要临时引导安装暴露的是安装边界本身不合适。同时，先承诺指令形状、后检查底层命令能否实现，造成返工。

**后续要求：** 影响整体方案的底层限制应优先用帮助或最小调用核实。Rust 配套工具默认沿用 Cargo 安装与版本管理；不同于生态默认的安装依赖或目录布局，须有实际需求依据。不要无依据增加第二套包管理。

本次最终采用 cargo install miresidian_cli 安装入口，再由 cargo miresidian install --full 安装独立后端；--full 属于 CLI 子命令，不能扩展原生 cargo install。工具位于 Cargo 安装根目录，同根替换当前版本；不是默认多版本并存。完整系统构建环境自动配置仍是单独待办，不能把“工具已安装”写成“环境已配齐”。

### 10.4 接受局部建议时缺少整体推演，需求也未完整落地

**踩坑表现：** 在全局/项目内安装等讨论中，局部方案不断修补；用户要求的两个框架版本别名、命令层级、构建与打包职责、平台与位数等事项，需要逐项再次纠正和补充。

**为什么踩坑：** 我把“及时回应用户”误当成接受每个局部方案，没有检查它与已确定边界是否冲突，也没有把已接受要求保留为实现约束。沟通完成被错误地当成需求已进入代码、帮助和文档。

**后续要求：** 对影响流程的选择，用首次安装、新建项目、已有项目、升级/降级和失败恢复等相关场景做简短推演。用一份简要的已接受要求记录核对最终实现、帮助与示例，保留别名等精确要求。发现设计矛盾时指出原因并给出可执行修正，不以持续增加特例掩盖矛盾；简单任务不额外建立庞大管理文档。

### 10.5 Skill 偏成工具手册，遗漏 Node 开发的关键决策

**踩坑表现：** 第一版 skill 大量描述工具怎么调用，Node 需求设计、业务实现与验收成为次要内容。重写后，对 features 仍只提概念，没有完整说明如何选择、配置、声明和验证。初期也只安装了本地副本，未同时纳入框架仓库维护。

**为什么踩坑：** 我沿用了刚完成工具链工作的材料和思路，按手头信息写作，没有从下一位 AI 需要完成的 Node 任务反推内容。把“包含工具用法”当成“能指导完成项目”，又把格式/引用校验通过误当成内容覆盖充分。遗漏 features 并非无资料可查，而是没有逐项检查框架能力是否落实到项目配置和行为。

**后续要求：** 主文档围绕需求、Config/Input/Output 契约、项目结构、业务/通信、生命周期、验证和交付组织；工具用法放子文档。能力说明至少回答“何时需要、依赖如何配置、节点如何声明、运行时改变什么、如何取得验证证据”。例如 instances/lease 必须同时说明 Cargo features 与节点标注，不只列名称或盲开全部能力。

内容评审应能沿一个实际 Node 需求找到实现与验收依据，不以文档篇幅或校验器通过作为充分条件。完整 skill 已保存在 [skills/miresidian-node](../skills/miresidian-node/SKILL.md)，两份副本按 AGENTS 中的规则同步，包含引用、元数据和新增文件。

### 10.6 验证范围失控：把“更多检查”当作“更可靠交付”

**踩坑表现：** 局部工具/文档修改被扩展到全工作区、多平台和宿主环境问题；已有通过结果没有充分复用，构建、检查、状态读取和日志输出存在重复。用户反馈大量时间和 AI 用量消耗在验证上。

**为什么踩坑：** 我没有先明确每个检查要回答的问题、已有证据何时失效，以及什么条件满足后应停止。面对不确定性时倾向增加检查，用“更全面”缓解不确定，却没有评估它是否改变本次交付结论。原有全量检查清单也被机械套用，没有按实际修改选择范围。

检查发现新的环境问题后，我又把它们直接纳入当前任务，导致验证成为新的工作来源。缺少阶段性的必要性判断，使一次已经足够的验证继续消耗时间。频繁轮询和读取整段日志进一步增加了 AI 用量。

**后续要求：** 执行前明确本次改动、交付目标、最小所需证据和可复用结果；每项新增检查必须对应未被回答的问题。修复后优先重跑失败项和直接受影响项。耗时超出预估时重新判断必要性；不因出现无关失败就自动扩大任务。满足停止条件后结束，具体范围规则见本规范第 7 节。

例如，纯 skill/规范修改检查内容与引用；dlltool 参数修复验证相关 Windows 调用和目标构建；只有实际影响共享运行时或多个组件时，才扩大到对应回归。两种位数都受影响时检查两种位数，不据此推导出必须重跑所有框架和工具测试。

### 10.7 从“验证过多”摆到“取消必要验证”

**踩坑表现：** 用户批评扩大验证后，我取消了整条 CI。取消发生在 MinGW 安装阶段，修复后的参数和 Windows 构建尚未执行，随后只能报告“已修改，但未验证通过”，又让用户再次推动执行。

**为什么踩坑：** 我把纠正理解为对上一动作的否定，按情绪变化选择相反动作，没有保持“质量证据必须具备、成本必须受控”这两个同时成立的目标。为了迅速表现出收缩范围，取消了与故障直接相关的必要检查。

**后续要求：** 先区分必要检查与无关检查，只停止后者；不能把没有证据的修改当作修复完成。若现有 CI 一个作业串联了相关和无关步骤，应选择相关作业、以目标步骤结果记录证据，并停止后续无关工作。只有任务不再需要某项验证时才取消它，不以省时为由跳过直接受影响的行为。

本次最终只重跑 Windows 作业；x64/x86 构建、DLL 加载/卸载步骤成功后，停止后续工具测试，再发布框架。工作流因后续步骤被取消而显示 cancelled，不应据此否认已成功的目标步骤，也不能反过来宣称整条 CI 全绿。

### 10.8 Windows 配置修复只验证“看起来合法”，未验证参数实际传递

**踩坑表现：** Windows CI 先后暴露 MSYS2 路径假设、PATH 中工具位数选择，以及 dlltool 路径双引号问题。最后一种把引号保留为文件名内容，rustc 调用的路径形如 '"D:/.../dlltool.exe"'，因此返回 Windows 文件名语法错误。参数修复见提交 8b51d7f。

**为什么踩坑：** 我用本地熟悉的路径和命令解析经验推断远端环境，没有始终采用环境实际输出。参数经过 YAML、PowerShell、环境文件、Cargo、rustc 和 Windows 进程创建，不是单层 shell 命令；给环境变量值增加引号，并不保证下游把它当成转义语法。我确认了选项存在和配置格式，却没有取得这条完整调用链成功的证据。

同样，滚动 stable 的 lint 差异、Windows 默认日志编码等，说明验证环境与既有结果的对应关系必须明确。某条库测试通过或某个版本支持参数，不足以证明宿主工具组合配置正确。

**后续要求：** 使用 action/环境提供的真实路径；明确链接器和 dlltool 的目标位数。排查时查看下游实际收到的参数，区分语法引号和字面字符。对跨进程参数修复，以相关目标实际构建为证据，不以静态字符串检查替代。不要为修复一个已知路径问题重建整个环境方案。

### 10.9 技术状态解释不完整，让用户承担判断与推动责任

**踩坑表现：** 发布状态、框架验证、工具套件验证和 Windows CI 失败被混在较长汇报中；“Windows CI 仍未修复”没有及时讲清失败阶段、原因和实际影响。指出执行错误后，有时停在解释和承诺，没有完成仍在授权范围内的必要工作。

**为什么踩坑：** 我按执行顺序描述过程，没有围绕用户需要作出的判断报告结论。虽然没有把失败写成通过，但只列状态没有说明其意义，也没有承担直接相关问题的闭环责任。诚实披露是必要条件，不能代替完成任务。

**后续要求：** 先给出当前交付结论，再说明阻塞的具体步骤、受影响对象和下一步。在已授权范围内继续完成必要动作；用户询问状态本身不自动授权新的设计、改动或发布。说明 CI 配置失败时，不暗示已经确认运行时/DLL 故障；说明部分步骤通过时，不夸大为全量验证完成。

### 10.10 发布判断要区分组件、版本和证据的不同作用

**踩坑表现：** 会话中需要反复确认 CLI 从独立版本起步、同一 Cargo 安装根目录的版本替换行为，以及框架发布是否会重复上传所有子项目。旧组件标签与当前清单存在管理方式上的差异，也不能直接据此推断有未发布功能。

**为什么踩坑：** 我没有始终把“统一入口/发行”“独立 crate 版本”“依赖可用性”“源码标签”和“registry 上传”分别看待。若只看本地版本或标签差异就发布，会把管理性变更误当成功能更新，或无差别重发整个工作区。

**后续要求：** 发布前形成实际候选列表：各组件本地版本、真实已发布版本、实质变更与待发布依赖。只发布本次需要且尚未发布的组件；依赖版本已可用则直接复用，不联动升版。无需补发开发中间版本，不为统一发布要求所有组件同号。Cargo 包验证、registry 发布成功和 Git 源码可访问分别核对，不重复执行等价 dry-run 与正式发布验证。

本次工具发布为 CLI 0.2.1、Pack/TestFlow 各 0.12.0；之后框架发布只上传根 crate 0.16.5、0.16.6，未重复发布已有子库与工具。这些是本次事实，不是以后应固定采用的版本号。

### 10.11 错用版本标签检查，静态路径假设又制造额外排查

**踩坑表现：** 在纯规范提交之后，曾对各独立组件直接执行要求标签指向当前 HEAD 的检查，得到失败；但组件标签本应停留在各自版本提交。发布后还假设归档必然保留在固定 target/package 路径，读取不存在的文件，产生额外工具调用。

**为什么踩坑：** 我把检查命令的适用条件当成通用条件，没有先确认它检查的是“版本提交”还是“当前工作树”。对临时构建产物也用预期路径代替实际可用状态。这些验证自身的错误被误当成需要继续排查的产品问题，进一步拉长了任务。

**后续要求：** 版本提交后执行规定的标签核对；之后只有纯规范变更时，不移动旧标签，检查该提交适用的版本门禁，并核对原标签快照和组件内容。不能为让检查通过而改写标签，也不能把当前 HEAD 不等于旧版本提交写成产品失败。

读取归档前先确定实际产物是否仍存在；只有发布确认确实需要时，才读取 Cargo 实际产物或 registry 真实发布包。已取得足够发布证据后，不再追加文件检查来制造新的完成条件。

### 10.12 后续执行时的最小决策检查

开始相关工作及收到用户纠正后，重新核对以下问题；简单任务用简短说明即可，不把本复盘变成新的繁重审批或全量检查流程：

1. **目标是什么？** 当前是在完成 Node 业务、维护 skill、修改工具还是发布组件？最近的提问是否只是要求解释状态？
2. **哪些边界必须保持？** 已确认的项目独立性、Cargo 管理方式、版本别名、交付平台和用户授权是什么？
3. **什么证据足够？** 每项检查回答什么问题，哪些既有结果仍有效，哪些失败直接阻断交付？
4. **何时停止？** 必要证据齐备后立即交付；缺什么就处理什么，不默认增加更多组件、平台、依赖或环境工作。
5. **交付是否真的成立？** 真实业务、相关能力配置、必要验证、版本/产物和实际发布状态是否各有依据？不把解释、计划、模板或工具运行成功当作项目完成。

这次最应改变的是判断方式：保留用户的完整目标，主动指出设计矛盾，按因果关系选择验证，在足够证据上完成交付。不能只记住“少跑测试”或“多写文档”，否则仍会在过度执行与交付不足之间反复。
